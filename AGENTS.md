# LUNA development

Follow the parent workspace instructions. Work from this repository root, read `Cargo.toml` and the relevant crate before changing code, and preserve unrelated work. Use `--locked` for normal Cargo verification.

After completing a feature and its required checks, follow [the commit-and-push skill](.codex/skills/commit-and-push/SKILL.md) to clean up task artifacts, commit all feature changes, merge into `main` if needed, and push and verify `origin/main`. Honor an explicit user request to stop earlier.

## Repository pending tasks

For requests to pick up, resume, organize or add pending work, use the shared
[task queue](docs/pending-tasks/README.md) and its
[agent workflow](docs/pending-tasks/WORKFLOW.md). Claim atomically through
`python3 scripts/pending_tasks.py claim --owner <agent-name> --session <actual-chat-or-run-id>`
before implementation; inspect prior work and linked specifications. Respect
dependency/code-area reservations, heartbeat active work, checkpoint evidenced
criteria, and pause/block unfinished work with a useful resume note. Do not
treat a stale Markdown status or expired lease as permission to duplicate work.
New tasks use the catalog intake path; repository queue status and LUNA Board
runtime status have separate owners.

## Tests

Write, change, review and sweep tests through [the test-audit skill](.codex/skills/test-audit/SKILL.md); it is the default way to test in this repository. Every new or changed test passes its authoring gate: it names the behavior and the credible regression it catches, has one owner at the strongest real boundary (prefer end-to-end and integration suites), and needs no test-only production seam. Use its campaign mode ([CAMPAIGN.md](.codex/skills/test-audit/CAMPAIGN.md)) for whole-crate sweeps. Codex finds the skill through `.agents/skills` and Claude Code through `.claude/skills`; both link to `.codex/skills`.

## App channels and product versions

- Read [the local release workflow](docs/reference/local-release-workflow.md) before changing product versions, packaging, or publishing. The product version starts at `0.0.1`; the independently versioned SDK and protocol/schema versions keep their own contracts.
- For each completed behavior change, classify its version impact before building: `patch` for compatible fixes and behavior-preserving performance improvements; `minor` for new user-facing features and pre-1.0 breaking changes; no bump for docs, tests alone, formatting, or a behavior-preserving refactor. Use `python3 scripts/version.py bump <patch|minor>` once per feature/PR, choosing the highest impact. Do not bump repeatedly for each edit or duplicate a bump already made for the same work. Update `CHANGELOG.md` with the user-visible result and any compatibility impact. Never bump to `1.0.0` without explicit user authorization.
- **LUNA Alpha** is the frozen daily-use app at `~/Applications/LUNA Alpha.app`, with data at `~/.luna-alpha` and IPC `59779`. Never rebuild, replace, migrate, reset, or delete this app/data as part of ordinary ticket work or cache cleanup. Only an explicit user request to install or update Alpha authorizes `python3 scripts/macos-app.py install-alpha` or `update-alpha`. A version bump, commit, merge, or push does not authorize promotion.
- Normal coding and ticket work use **LUNA Dev**. Run `python3 scripts/macos-app.py dev` to gracefully leave Alpha and refresh Dev; this calls the existing guarded refresh workflow. If saving/quit fails, preserve both bundles and report the blocker. Do not force-quit either app. `python3 scripts/macos-app.py alpha` opens the installed snapshot without rebuilding it, only when returning to daily use is requested.
- Preparing or pushing source is separate from publishing a release. `python3 scripts/version.py release-plan` is read-only. Never create/push a release tag, publish a GitHub Release, or promote an installed Alpha unless the user explicitly requests that action. Ordinary features still finish on `origin/main` through commit-and-push.

## macOS developer app handoff

- After each meaningful LUNA code change and its relevant checks, run `python3 scripts/macos-app.py dev` yourself so the user gets a new **LUNA Dev** app to try. It switches safely and calls `scripts/run-macos-dev.sh --refresh`, using the same incremental Cargo cache. Do not ask the user to build, reinstall, or run the command. Explicit Alpha installation/update work may finish with Alpha running after the Dev and Alpha verification steps.
- Confirm the refreshed app's exact bundle process is running, its expected IPC port is listening, and `codesign --verify --deep --strict 'target/luna-macos-dev/LUNA Dev.app'` succeeds before reporting it ready. Report the build time and any limitation that affects testing.
- The refresh command replaces one bundle under `target/luna-macos-dev/` and removes its temporary previous bundle. Preserve the dev data directory and `target/debug` cache. If a build fails or LUNA Dev declines to quit because of unsaved work, leave the current app intact and report the blocker; never force-quit it just to refresh.
- Run only one Luna GUI app at a time, including QA and installed copies. `run-macos-dev.sh` refuses a second running Luna app and serializes app operations across linked worktrees. Before native QA, let the current app save and quit gracefully; never force-quit it to free the slot. QA worktrees still require all four `LUNA_DEV_APP_NAME`, `LUNA_DEV_BUNDLE_ID`, `LUNA_DEV_IPC_PORT`, and `LUNA_DEV_DATA_DIR` overrides from [the QA guide](docs/reference/qa-infrastructure.md). Verify the chosen app's process, port and signature. Never refresh main's identity from a QA worktree.
- After a QA milestone is reviewed, preserve and hash its evidence, confirm no process or task needs its bundle, quit that exact QA app gracefully, then unregister and remove only its scoped disposable bundle. Preserve its data and the shared build cache unless a separately reviewed cleanup covers them. Reopen the primary `LUNA Dev` app for the user's handoff only after the QA app is stopped.

## Rust build and disk hygiene

- Use `scripts/cargo.sh` in place of `cargo` for local builds, checks, tests and Clippy. It uses Mr Boxington (`mbx`, validated with **1.18.0**) when installed and falls back to Cargo when absent. Prefer `scripts/cargo.sh check --locked -p <package>` for fast feedback, then focused tests for the changed crate. Run broad workspace builds only when the change actually requires them. Avoid repeatedly compiling the large UI dependency graph for an engine-only change.
- `scripts/run-macos-dev.sh --refresh` already uses the wrapper. Use `LUNA_BUILD_CACHE=1` to require mbx, or `LUNA_BUILD_CACHE=0` to diagnose with plain Cargo. Never silently retry a failed cached build. Preserve `--locked`, toolchain, features and profile between equivalent builds.
- Read [the build-cache guide](docs/reference/build-cache.md) before changing cache policy. `.mbx.toml` preserves Cargo incremental mode and source paths; the wrapper disables managed targets, learned incremental state and hard-link restoration, and defaults the action-store GC budget to **20 GiB**. This budget is separate from `target/debug` and is enforced during collection, not a hard instantaneous disk cap.
- Do not run `mbx setup`, `mbx adopt`, `mbx clean`, or `mbx cache remove` for this checkout: `target/` contains the app and its data. Do not introduce global Cargo wrapping, a remote cache or a new linker as part of routine work. Use `mbx cache stats --json` to inspect reuse/storage and `MBX_GC_MAX_SIZE=20GiB mbx gc --dry-run` to preview action-store collection. Keep cleanup scoped and coordinate with active tasks.
- To validate changes to the cache integration, run `scripts/verify-build-cache.sh`; retain its log/JSON artifact directory. Its two disposable target directories are an explicit exception to the usual target-reuse rule and are removed by the verifier.
- Reuse this repository's `target/` cache. An explicitly authorized isolated audit worktree owns its own `target/`; preserve it while the audit/app needs it. `scripts/cargo.sh` serializes builds across all linked worktrees with a shared Git-directory lock. Exit 75 means busy or budget-blocked: inspect the owner/accounting, coordinate, then retry; do not bypass the guard or repeatedly poll.
- The build guard trims old duplicate `target/debug/incremental/` directories under its lock when that cache exceeds 12 GiB. It keeps two recent variants per crate and anything used in the past 24 hours. Preview with `python3 scripts/prune_incremental.py`; do not expand this automatic cleanup to `deps`, apps, user data, or other target directories.
- The aggregate operating ceiling is **170 GiB**, with **30 GiB headroom below the absolute 200 GiB policy maximum**. It includes every linked checkout's entire `target/` and the shared mbx cache root. Each build reserves up to **25 GiB** growth, samples usage while running, and stops its own process group on a breach. Run `python3 scripts/build-budget.py --status` before planning additional builds. The wrapper must be present in main and peers before opening parallel build work; direct Cargo or unrelated cache writers are outside this cooperative lock. Polling is not a filesystem quota: stop work and coordinate if outside writes consume headroom. See the build-cache guide for accounting limits.
- For one-off validation or CI-like runs, use `CARGO_INCREMENTAL=0` to avoid growing `target/debug/incremental`. Keep incremental compilation for an interactive edit loop when its faster rebuilds are worth the disk cost. Do not alternate build flags needlessly: changed profile or rustflags settings can cause extra rebuilds.
- At the end of every task, remove only task-created temporary build directories, disposable fixtures and reviewed QA bundles as described above, then check `du -sh target/debug target/release` and available disk space. Preserve source, Git state, user data, the current primary app, active QA apps, and outputs another task is using.
- If one `target/debug` exceeds **70 GiB**, or aggregate admission is blocked, coordinate with active tasks before cleanup. The aggregate limit takes precedence; 70 GiB is a cleanup review threshold, not an allocation per worktree. Check that no Cargo/rustc process or open file is using the selected target, run `cargo clean --dry-run --profile dev --target-dir` with its verified absolute `target` path, inspect the scope, then clean that **dev profile only** when it will not interrupt another task. Never run unqualified `cargo clean` or recursively delete the repository/workspace. Verify `du`, `df`, and `git status` afterward. Full clean is a milestone/size-pressure action, not an after-every-edit habit.
- If builds grow rapidly again, measure a dev-profile change before applying it. The Cargo Book recommends `debug = "line-tables-only"` for workspace crates and `debug = false` for dependencies, with a separate full-debug profile when debugger variables are needed. Preserve native-debugging needs and benchmark the trade-off before changing `Cargo.toml`.
