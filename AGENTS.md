# LUNA development

Follow the parent workspace instructions. Work from this repository root, read `Cargo.toml` and the relevant crate before changing code, and preserve unrelated work. Use `--locked` for normal Cargo verification.

## macOS developer app handoff

- After each meaningful LUNA code change and its relevant checks, run `scripts/run-macos-dev.sh --refresh` yourself so the user gets a new **LUNA Dev** app to try. Do not ask the user to build, reinstall, or run the command. This handles UI and engine changes with the same incremental Cargo cache.
- Confirm the refreshed app's exact bundle process is running, its expected IPC port is listening, and `codesign --verify --deep --strict 'target/luna-macos-dev/LUNA Dev.app'` succeeds before reporting it ready. Report the build time and any limitation that affects testing.
- The refresh command replaces one bundle under `target/luna-macos-dev/` and removes its temporary previous bundle. Preserve the dev data directory and `target/debug` cache. If a build fails or LUNA Dev declines to quit because of unsaved work, leave the current app intact and report the blocker; never force-quit it just to refresh.

## Rust build and disk hygiene

- Use `scripts/cargo.sh` in place of `cargo` for local builds, checks, tests and Clippy. It uses Mr Boxington (`mbx`, validated with **1.18.0**) when installed and falls back to Cargo when absent. Prefer `scripts/cargo.sh check --locked -p <package>` for fast feedback, then focused tests for the changed crate. Run broad workspace builds only when the change actually requires them. Avoid repeatedly compiling the large UI dependency graph for an engine-only change.
- `scripts/run-macos-dev.sh --refresh` already uses the wrapper. Use `LUNA_BUILD_CACHE=1` to require mbx, or `LUNA_BUILD_CACHE=0` to diagnose with plain Cargo. Never silently retry a failed cached build. Preserve `--locked`, toolchain, features and profile between equivalent builds.
- Read [the build-cache guide](docs/reference/build-cache.md) before changing cache policy. `.mbx.toml` preserves Cargo incremental mode and source paths; the wrapper disables managed targets, learned incremental state and hard-link restoration, and defaults the action-store GC budget to **20 GiB**. This budget is separate from `target/debug` and is enforced during collection, not a hard instantaneous disk cap.
- Do not run `mbx setup`, `mbx adopt`, `mbx clean`, or `mbx cache remove` for this checkout: `target/` contains the app and its data. Do not introduce global Cargo wrapping, a remote cache or a new linker as part of routine work. Use `mbx cache stats --json` to inspect reuse/storage and `MBX_GC_MAX_SIZE=20GiB mbx gc --dry-run` to preview action-store collection. Keep cleanup scoped and coordinate with active tasks.
- To validate changes to the cache integration, run `scripts/verify-build-cache.sh`; retain its log/JSON artifact directory. Its two disposable target directories are an explicit exception to the usual target-reuse rule and are removed by the verifier.
- Reuse this repository's `target/` cache; do not create a new `CARGO_TARGET_DIR` per task. If isolation requires a separate target directory, record its exact path and clean that directory when the task finishes. Serialize expensive Cargo builds that share a target directory.
- For one-off validation or CI-like runs, use `CARGO_INCREMENTAL=0` to avoid growing `target/debug/incremental`. Keep incremental compilation for an interactive edit loop when its faster rebuilds are worth the disk cost. Do not alternate build flags needlessly: changed profile or rustflags settings can cause extra rebuilds.
- At the end of every task, remove only task-created temporary build directories and disposable fixtures, then check `du -sh target/debug target/release` and available disk space. Preserve source, Git state, user data, packaged apps, and outputs another task is using.
- If `target/debug` exceeds **50 GiB**, coordinate with any active task first. Check that no Cargo/rustc process or open file is using it, run `cargo clean --dry-run --profile dev --target-dir` with this checkout's verified absolute `target` path, inspect the scope, then clean that **dev profile only** when it will not interrupt another task. Never run unqualified `cargo clean` or recursively delete the repository/workspace. Verify `du`, `df`, and `git status` afterward. Full clean is a milestone/size-pressure action, not an after-every-edit habit.
- If builds grow rapidly again, measure a dev-profile change before applying it. The Cargo Book recommends `debug = "line-tables-only"` for workspace crates and `debug = false` for dependencies, with a separate full-debug profile when debugger variables are needed. Preserve native-debugging needs and benchmark the trade-off before changing `Cargo.toml`.

References: [Cargo build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html), [build-performance guidance](https://doc.rust-lang.org/cargo/guide/build-performance.html), [profile settings](https://doc.rust-lang.org/cargo/reference/profiles.html), and [scoped `cargo clean`](https://doc.rust-lang.org/cargo/commands/cargo-clean.html).
