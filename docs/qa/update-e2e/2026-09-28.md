## GUI one-click fixture failure cases

Before preparing a second local release, check these boundaries:

1. Refuse a missing, running, unsigned, wrong-identity, or wrong-version QA
   source bundle. Never modify the primary bundle or either app's data.
2. Refuse a missing or invalid prior **test** signing key, a mismatched public
   key, an unexpected archive member, or an invalidly signed candidate app.
3. Sign the exact JSON bytes, require a SHA-256 matching the served asset, and
   use a versioned same-origin URL. A failed fixture or HTTP start must stop
   only its own server child and retain evidence of the failure.
4. Keep the valid fixture server available while the coordinator launches the
   QA app with the test feed/key, presses Update in the native UI, and reads
   back the new bundle/process. Never launch or quit an app from the fixture
   preparation script.
