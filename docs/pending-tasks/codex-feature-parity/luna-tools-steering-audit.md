## How a Codex tool becomes a visible Luna row

The Codex app-server sends `item/started` and `item/completed`; Luna's adapter maps those through `normalize::map_item` to typed `AgentEvent::ToolCall/ToolResult` ([LUNA crates/harness/src/codex/mod.rs:1524-1627](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/codex/mod.rs#L1524), [LUNA crates/harness/src/codex/normalize.rs:1037-1043](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/codex/normalize.rs#L1037)). The session engine appends normalized events to the host run journal and broadcasts them ([LUNA crates/engine/src/sessions.rs:5183-5196,7319-7343](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/sessions.rs#L5183)). The document fold creates one `MessagePart::Tool` by item ID, then resolves it in place with outcome, one-line output summary, output/diff byte count, and journal reference ([LUNA crates/doc/src/parts.rs:404-472,659-679](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/doc/src/parts.rs#L404)). Tool inputs that may contain sensitive content are sanitized before doc persistence: file content, edit strings, web-fetch prompt, MCP/unknown arguments; command/path/query labels remain (`:710-744`). The UI groups consecutive tools into expandable chips, keeping subagent spawns separate; it displays invocation, status, summary/diff stats, and lazy FetchToolBlob controls ([LUNA crates/ui/src/transcript.rs:1392-1440,6702-6815,7180-7225](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/ui/src/transcript.rs#L1392)). The fetch goes to the owning host's normalized run journal (`:4689-4747`, [LUNA crates/engine/src/rpc.rs:10432-10456](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/rpc.rs#L10432)). This is a real output/history path; the September 25 QA note saying full stdout could not be disclosed predates the later lazy-journal work.

## Steering while tools run

The UI default for a busy follow-up is durable **Queue**, not Steer ([LUNA crates/proto/src/task_command.rs:9-17](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/proto/src/task_command.rs#L9), [LUNA crates/ui/src/composer.rs:9030-9055](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/ui/src/composer.rs#L9030)). Selecting Steer creates a durable row and attempts native Steer now while the turn is active ([LUNA crates/ui/src/composer.rs:9744-9766](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/ui/src/composer.rs#L9744); [LUNA crates/engine/src/rpc.rs:5877-5915](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/rpc.rs#L5877)). The direct action is narrow: active-turn/readiness and queue revision fences, one explicit steer in flight, no image attachments, and no automatic interrupt fallback ([LUNA crates/engine/src/sessions.rs:3502-3586](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/sessions.rs#L3502), [LUNA crates/engine/src/rpc.rs:3185-3198](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/rpc.rs#L3185), [LUNA crates/engine/src/doc_host.rs:5033-5112,5717-5735](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/doc_host.rs#L5033)). The UI calls Steer now "without interrupting" and calls Send now "interrupts an active response" ([LUNA crates/ui/src/queue.rs:103-120](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/ui/src/queue.rs#L103)). Stop is separate: the engine sends cancellation; Codex adapter sends `turn/interrupt` and later escalates process signals if needed ([LUNA crates/engine/src/sessions.rs:3590-3641](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/sessions.rs#L3590), [LUNA crates/harness/src/codex/mod.rs:1997-2031](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/codex/mod.rs#L1997)). Therefore an explicit Steer in Luna does not itself kill a running Read/Run/Edit tool.

The adapter sends native `turn/steer` with `expectedTurnId` from its active turn router and accepts only a reply whose `turnId` matches ([LUNA crates/harness/src/codex/mod.rs:1858-1913](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/codex/mod.rs#L1858)). Codex current source checks that turn and appends input to the pending queue, returning the same turn ID **before model incorporation** ([Codex codex-rs/app-server/src/request_processors/turn_processor.rs:1024-1162](https://github.com/openai/codex/blob/ceea67163f93b4317c9352d1cd2af9fee32537b9/codex-rs/app-server/src/request_processors/turn_processor.rs#L1024); [Codex codex-rs/core/src/session/turn_input.rs:655-741](https://github.com/openai/codex/blob/ceea67163f93b4317c9352d1cd2af9fee32537b9/codex-rs/core/src/session/turn_input.rs#L655)). Late tool results after the split are journaled and resolved on the original tool part above that user bubble ([LUNA crates/engine/src/sessions.rs:6911-6967](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/engine/src/sessions.rs#L6911); [LUNA crates/doc/src/schema.rs:885-945](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/doc/src/schema.rs#L885)). **Main semantic gap:** Codex's matching `turn/steer` reply proves queued acceptance, not model read. Codex 0.159 offers optional `clientUserMessageId`; Luna has a stable `SteerMessage.message_id` but does not send it ([LUNA crates/harness/src/lib.rs:60-67](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/lib.rs#L60); [LUNA crates/harness/src/codex/mod.rs:1858-1863](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/crates/harness/src/codex/mod.rs#L1858)). Codex later emits `userMessage.clientId` and preserves it in `thread/read`, which could verify user-message recording; it is **not idempotent** and still does not prove model consumption ([Codex codex-rs/app-server-protocol/src/protocol/v2/item.rs:239-242,869-875](https://github.com/openai/codex/blob/ceea67163f93b4317c9352d1cd2af9fee32537b9/codex-rs/app-server-protocol/src/protocol/v2/item.rs#L239); [Codex codex-rs/core/src/session/turn_input.rs:717-741](https://github.com/openai/codex/blob/ceea67163f93b4317c9352d1cd2af9fee32537b9/codex-rs/core/src/session/turn_input.rs#L717)). ## Smallest repeatable E2E matrix to close the source-only gaps

Use one disposable local Codex task/workspace and a fixed provider version/model, plus a deterministic fake app-server for rare failure frames. Save redacted `thread/read` JSON and Luna `WatchDocMessages`, `WatchQueue`, task-command receipts, normalized event journal excerpt, CLI version/config feature flags, and git SHA together. The prior QA document gives the concrete `rpc_probe` readback pattern ([LUNA docs/qa/chat-ordering-comparison-2026-09-25.md:69-96](https://github.com/novnski/luna/blob/e71d90caad0798ca6dcec28da4b352d8f8c39c0c/docs/qa/chat-ordering-comparison-2026-09-25.md#L69)). Prefer source-derived assertions over a screenshot alone.
