## What is actually recent

### Goal runtime and Plan nuance

The goal engine is **already part of normal stock app-server execution** when the persistent state database is available and `Feature::Goals` remains enabled. The app server installs the goal extension from its ordinary `thread_extensions` path (`codex-rs/app-server/src/message_processor.rs:322-355`, `.../src/extensions.rs:74-88`); `Goals` is stable/default on (`codex-rs/features/src/lib.rs:1704-1707`). For a persistent non-review thread, the extension publishes model-visible `get_goal`, `create_goal`, and `update_goal` tools (`codex-rs/ext/goal/src/extension.rs:102-161,529-584`, `.../src/spec.rs:9-11`). Their descriptions require explicit user/system/developer intent to create a goal; an ordinary coding request does **not** automatically create one (`.../src/spec.rs:25-48`). Ephemeral threads retain tool specs but execution is rejected (`.../src/tool.rs:167-177`). The app can also create or manage a goal through stable `thread/goal/set,get,clear` RPCs.

Once a goal is active, the extension listens for idle turns and internally calls `start_turn_if_idle` with a goal continuation input and `turnTrigger: "goal"`; no client `turn/start` is needed (`.../src/extension.rs:180-192`, `.../src/runtime.rs:425-505`). On normal turn completion, core sends `TurnComplete` and then invokes idle lifecycle (`codex-rs/core/src/tasks/mod.rs:843-879`). Thus an app may observe `turn/completed` **before** the goal continuation's `turn/started`; treating that first completion as end of the entire goal or unsubscribing/interrupting immediately can hide or stop continuation. The app should keep the thread subscription, show `thread/goal/updated` state, and wait for goal terminal status or subsequent turns. App-server notifications include `thread/goal/updated` and `thread/goal/cleared` (`codex-rs/app-server-protocol/src/protocol/common.rs:1929-1930`). A disabled flag, missing persistent state, ephemeral/review thread, explicit pause/block/complete, budget or usage limit, failed turn, pending user work, or unavailable live thread can prevent continuation (`.../ext/goal/src/extension.rs:102-111,301-420`; `.../ext/goal/src/runtime.rs:425-467`; `.../core/src/tasks/lifecycle.rs:59-84`). No LUNA-specific runtime proof was performed. If LUNA uses stock app-server, its likely gap is goal creation/control/visibility and handling of multi-turn completion, **not absence of the underlying engine**.

The native `turn/start.collaborationMode` field used to select preset Plan mode is explicitly **experimental** (`codex-rs/app-server-protocol/src/protocol/v2/turn.rs:260-267`), including in installed 0.159.0. Plan text and `turn/plan/updated` progress notifications remain native output surfaces (`.../v2/item.rs:274-279`; `.../v2/turn.rs:565-590`); a client can render those without claiming Plan-mode selection is stable. The TUI visibly offers Default and Plan modes (`codex-rs/protocol/src/config_types.rs:669-701`). Plan turns do not count as an active goal turn in goal accounting (`codex-rs/ext/goal/src/extension.rs:257-263`).

## Prioritized parity candidates for LUNA cross-check

1. Native review UI: `review/start` with working tree, branch, commit, and custom target. High daily utility, stable API. Confirm adapter event rendering and user-facing trigger.
2. Native conversation rewind/edit: `thread/revert` with explicit file-state separation and history rehydration. High daily utility, stable API; do not conflate with Git/checkpoint undo.
3. Lossless rich items and prompt inputs: image generation, web search, MCP app UI, fileId/local/inline images, audio, skill/mention, persisted thread attachments. High utility for multimodal and plugin workflows; render unknown items generically until typed support lands.
4. Settings/discovery UX: model capabilities and service tiers, effective config/requirements, MCP OAuth health, plugin/app browsing and install, skills/hooks. High utility, all have stable base APIs; respect backend/enterprise/experimental gates.
5. Approval fidelity: stdin vs command, per-turn/session permission grants, environment and network context, proposed rules, MCP elicitation, user-input and dynamic tool callbacks. High trust impact; prevent missing callback types from stalling turns.
6. Thread goals and true editable queue. Goals are stable and useful for long-running work; the queue is experimental and may be a later phase if LUNA's own queue is already reliable.
7. Realtime voice and live turn settings. Interesting differentiated UX but experimental RPCs; verify account/backend readiness before committing design.

## TUI-specific vs harness behavior

`codex-rs/tui/src/slash_command.rs:11-173` is a menu of commands, not a promise that each name is a separate native feature. `/copy`, `/export`, `/raw`, `/theme`, `/keymap`, `/pets`, `/statusline`, terminal transcript Mermaid, and `/tui` are TUI presentation/preferences. `/worktree`, `/agents`, `/side`, `/btw`, `/goal`, `/review`, `/voice`, `/plugins`, `/apps`, `/mcp`, `/memories` wrap a mixture of core/protocol features and client UI. The checked-out feature catalog marks `Worktrees`, `Collab`, `Apps`, `Plugins`, `CodexHooks`, `GuardianApproval`, `Goals`, `FastMode`, `RealtimeConversation`, and `ImageGeneration` stable/default on, while `MemoryTool` is stable/default off (`codex-rs/features/src/lib.rs:1159-1163,1226-1229,1314-1317,1332-1335,1368-1371,1386-1389,1464-1467,1554-1557,1650-1653,1704-1707,1782-1797`). `CodeMode` remains under development/default off (`.../features/src/lib.rs:1064-1067`); exposing it as standard Codex parity would be premature.
