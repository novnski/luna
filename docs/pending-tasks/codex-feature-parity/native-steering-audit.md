## Contract and event timeline

1. Client sends `turn/steer` with `threadId`, nonempty `input`, and the exact `expectedTurnId` of a currently active turn (`codex-rs/app-server-protocol/src/protocol/v2/turn.rs:293-322`). App-server loads the thread, validates direct input and size, and calls `thread.steer_turn` (`codex-rs/app-server/src/request_processors/turn_processor.rs:1024-1079`). `turn/start` has a separate start-or-steer path, whereas explicit `turn/steer` **never starts a new turn** (`codex-rs/core/src/codex_thread.rs:513-530`; `.../app-server/src/request_processors/turn_processor.rs:651-674`).
2. Under the active-turn lock, Core checks there is a live task, the turn ID still matches, the task is regular rather than review/compact, and input is nonempty. On success it appends the input to that turn's pending queue, preserving a client message ID and acceptance order, signals queue activity, and returns the existing turn ID (`codex-rs/core/src/session/turn_input.rs:655-741`; `codex-rs/core/src/session/input_queue.rs:321-332`). If no turn, mismatch, non-steerable task or empty input, no message is appended; app-server returns an error (`.../turn_processor.rs:1080-1162`). The lock makes the state check and enqueue atomic against the active-turn transition.
3. App-server's successful `TurnSteerResponse { turnId }` arrives once Core accepts the queue operation. It is **not** confirmation that the model has read the steer, that the user message has been persisted, or that a new model response has started. Core's own module documentation says it replies before hooks, in-memory model-context update, rollout persistence, and sampling (`codex-rs/core/src/session/turn_input.rs:1-9`). A later `item/started` user message with the supplied `clientUserMessageId` shows that the turn loop has recorded it; the following Responses request is stronger evidence the model was actually sent it (app-server integration test: `codex-rs/app-server/tests/suite/v2/turn_steer.rs:292-355`).
4. With normal/default steering, the active model response continues. Completed tool call items can launch local tool futures while the response is streaming; the sampling step drains all in-flight futures before returning (`codex-rs/core/src/session/turn.rs:2787-2793,3162-3171`). Then the regular turn loop notices pending input and loops instead of completing (`codex-rs/core/src/tasks/regular.rs:101-124`; `.../session/turn.rs:540-566`). It drains pending input, runs user-prompt hooks, records the user item/history, and builds the next model request (`.../session/turn.rs:426-445,499-533`; `.../session/input_queue.rs:353-385`). The response can include already-started command/MCP/dynamic-tool outputs and the steer. This is a **tool completion boundary**, not necessarily a successful tool: nonfatal tool errors and tool rejection can be represented in outputs; a terminal turn error can prevent any next model request.
5. Multiple accepted steers are appended in order and can be incorporated together in the next model request. An explicit integration test holds a dynamic tool, sends two steers, returns the real tool output, and checks both user messages in order and the output exactly once, with no turn abort (`codex-rs/core/tests/suite/pending_input.rs:1290-1384`). A steer that arrives just as a sampling pass ends is still detected by the regular task's pending-input check; an idle/mismatched request is rejected rather than silently converted into a new turn (`.../core/src/tasks/regular.rs:115-124`; `.../core/src/session/turn_input.rs:664-680`).

`clientUserMessageId` is a **correlation field, not an idempotency key**. App-server passes it into `TurnInput::UserInput.client_id` on both `turn/start` and `turn/steer` (`codex-rs/app-server/src/request_processors/turn_processor.rs:618,1068`). Core's accepted-steer path appends the input without a duplicate-ID lookup (`codex-rs/core/src/session/turn_input.rs:717-741`); when the turn loop records the user prompt, it copies the ID to emitted `UserMessageItem.client_id` (`codex-rs/core/src/session/mod.rs:4886-4945`). The v2 `userMessage.clientId` and history projection preserve the value (`codex-rs/app-server-protocol/src/protocol/v2/item.rs:239-242,869-875`; `.../protocol/thread_history.rs:503-519`). A client can match an accepted steer to a later recorded user item, but that item still does not prove the model read it. If a response is lost or unknown, blindly replaying with the same ID can enqueue a duplicate; reconcile through notifications/readback and the client's own delivery state first.

For command, web search, image generation, and parallel tools, the common rule is that `turn/steer` queues input while the active work continues. A command or other locally dispatched tool already in the in-flight set is awaited before the next model request. Hosted web/image work represented by the in-progress model response is likewise not replaced by a default steer; it reaches the response boundary first. Source does not guarantee each third-party operation can be cancelled, nor that every failure becomes a normal tool result. A fatal model/compaction/turn error may end the turn with an accepted steer not yet read by the model. The test suite explicitly preserves pending steer in durable history after terminal compaction failure without automatically retrying that failed turn (`codex-rs/core/tests/suite/pending_input.rs:2041-2049,2152-2227`).

## Opt-in instant interrupt and classic interrupt

`features.instant_interrupt = true` changes how quickly the **current model response** yields to accepted user input. It creates a per-step preemption token and watches the turn's pending user input (`codex-rs/core/src/session/mod.rs:3878-3882`; `.../session/input_queue.rs:245-265`; `.../session/turn.rs:1628-1635`). The stream receive is preemptible; Codex can send `response.interrupt` and drain a Responses Lite websocket, or drop an SSE stream, then proceed to a follow-up request (`.../session/turn.rs:2634-2662`; test `codex-rs/core/tests/suite/pending_input.rs:1137-1228`). It can skip tool calls that the old model response had **not yet emitted**. Already launched local tool futures are still drained before return (`.../session/turn.rs:3162-3171`), and a test confirms real held-tool output and two steers survive even when the original response has not completed (`.../pending_input.rs:1290-1388`). The flag also lets a long code-mode `exec`/`wait` observation yield a live cell rather than terminate the cell; source passes preemption to `yield_observation`, and tests verify the cell's result can later be retrieved (`codex-rs/code-mode/src/grpc_session/operations.rs:70-109,258-345`; `.../core/tests/suite/pending_input.rs:1394-1590,1684-1805`). Both code mode and this faster steering path are under-development/default-off in source.

`turn/interrupt` is a separate, destructive action: app-server submits `Op::Interrupt`, and its normal RPC response waits for Core's internal `TurnAborted` event (`codex-rs/app-server/src/request_processors/turn_processor.rs:1598-1641`). On the v2 app-server wire, clients observe `turn/completed` with `turn.status: "interrupted"`, rather than a `turn/aborted` method (`codex-rs/app-server-protocol/src/protocol/common.rs:1944-1946`; `.../protocol/v2/turn.rs:33-39,549-552`). Core cancels the active task and clears its pending input (`codex-rs/core/src/session/mod.rs:4977-4983`; `.../tasks/mod.rs:540-569,934-965`; `.../session/input_queue.rs:268-273`). Force-interrupting active code-mode cells is a **separate** `CodeModeInterrupt` feature, also default-off (`codex-rs/features/src/lib.rs:1088-1091`; `.../core/src/tasks/mod.rs:936-946`). Do not describe native steer as cancel or stop; do not promise classic interrupt forcibly kills every already detached/background process.

## Compatibility acceptance scenarios for later end-to-end checks

1. Hold a running command (or dynamic tool) in one turn; submit `turn/steer` with that turn's ID. The UI marks it *accepted/pending* after the RPC response, keeps the tool active, then shows its final output and the steered user item before the follow-up model answer. The turn completes with `turn.status: "completed"`, rather than `"interrupted"`.
2. Hold two parallel tool calls and send two steers. Both tool outcomes appear exactly once; both steer messages keep order and reach one or subsequent follow-up model requests within the same turn. Avoid asserting that either RPC acknowledgement means model incorporation.
3. Steer during an actively streaming model response with default `instant_interrupt` off. Later response items/tool calls are allowed to finish before the steer reaches a new model request. If the user's config explicitly enables instant interrupt, observe a shortened old response, preservation of already-started tool outputs, and no new unstarted old-response tool call.
4. Steer just after a turn ends or with a stale `expectedTurnId`; the request must fail and must not create a new turn or duplicate the message. A non-steerable review/compact turn and empty input must likewise fail with an actionable reason.
5. Trigger a nonfatal tool error, then steer: the model should receive a coherent error/output record plus the steer if the turn continues. Trigger a terminal failure: show that acceptance did not guarantee incorporation; preserve/recover the message for explicit retry without silently replaying a side-effecting command.
6. Send `turn/interrupt` during a held tool in a separate scenario. Expect `turn/completed` with `turn.status: "interrupted"` and loss of pending in-turn steer, rather than the safe completion behavior of `turn/steer`.

No code changes, model calls, or app launches were performed. These are proposed E2E scenarios, not tests already run for LUNA.
