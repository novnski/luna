## Verified connection model

The phone is a client of the same server as web/desktop. The environment retains provider credentials, execution, files and durable threads. HTTP carries descriptors, pairing/session bootstrap and snapshot reads; WebSocket carries typed RPC and subscriptions. LAN, tailnet, T3 Connect, and other routes change reachability, not execution ownership. The durable environment ID remains stable across endpoint changes. See [`docs/internals/remote.md` lines 3–29](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L3-L29), corroborated by the descriptor ID check in [`ConnectionResolver.authorize` lines 271–303](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/resolver.ts#L271-L303) and the initial WebSocket config ID check in [`RpcSession` lines 294–309](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L294-L309). Implication for LUNA direct V1: a phone should connect to a running LUNA host; the host remains the owner of agent processes, credentials, filesystem, and persisted conversations. Give the host a durable ID and reject an address that answers as another host before sending a saved credential.

Mobile composes the shared `Connection.layerWithOptions`, shell/thread snapshot loaders, and native platform adapters in [`apps/mobile/src/connection/runtime.ts` lines 19–60](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/runtime.ts#L19-L60). The shared layer starts the registry, relay compatibility watcher/discovery and onboarding in [`connection/layer.ts` lines 75–104](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/layer.ts#L75-L104). The mobile platform supplies no primary/local registration (`Stream.empty`) and explicitly rejects an SSH gateway as desktop-only in [`platform.ts` lines 220–249](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L220-L249). T3's mobile settings can show an environment reached by a desktop-managed SSH route only if another usable route exists; mobile cannot itself provision/restore SSH. This is a verified limitation, not a missing read of the UI.

## Pairing and entry paths

The **Add environment** screen offers a camera QR scanner and manual Address/Code fields. Camera permission is asked only when the user taps the scan card; a successful scan fills fields and parks the camera, while submitting calls `onConnectPress(pairingUrl, routeFor)` and closes on success. See [`ConnectionsNewRouteScreen.tsx` lines 54–69, 111–185, 225–275](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionsNewRouteScreen.tsx#L54-L69) ([scan/submit](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionsNewRouteScreen.tsx#L111-L185), [fields](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionsNewRouteScreen.tsx#L225-L275)). Manual input with a schemeless numeric IP chooses HTTP; a hostname chooses HTTPS, and an explicit scheme wins. Code is put in the URL fragment; parser accepts fragment or legacy query token and unwraps a hosted pairing link. QR extraction accepts a raw URL or `t3code:` payload carrying a `pairingUrl` query parameter. See [`pairing.ts` lines 30–92](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/pairing.ts#L30-L92); its existing tests explicitly cover IP/hostname defaults and wrapped QR payloads in [`pairing.test.ts` lines 10–59](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/pairing.test.ts#L10-L59).

**Important qualification:** production route prefill/auto-connect via incoming URL is deliberately disabled: `routePairingUrl` and `shouldAutoConnect` are gated behind `__DEV__` with a comment about attacker-chosen host/token; production pairing requires the scanned or manually entered user action. See [`ConnectionsNewRouteScreen.tsx` lines 53–60 and 188–195](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionsNewRouteScreen.tsx#L53-L60). The generic app-link filter recognizes `t3code://pair?pairingUrl=x` as a possible app link in a test, and QR extraction understands that payload, but that does **not** prove production inbound deep-link pairing auto-connect. Directly claiming that feature would overstate the source.

Shared onboarding parses the target, fetches the public descriptor, checks `expectedEnvironmentId` *before spending the one-time code* when adding a route to a saved machine, checks protocol compatibility, redeems the pairing credential, then registers a bearer route indexed by environment ID + address. Pairing the same machine at a new address adds a route; pairing the same address replaces that route. See [`ConnectionOnboarding.preparePairingRegistration` lines 95–163](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/onboarding.ts#L95-L163), wrapped by mobile's single-flight `connectPairingUrl` command in [`apps/mobile/src/connection/onboarding.ts` lines 11–31](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/onboarding.ts#L11-L31). The same link should be a fresh one-time credential for each new device, per [`docs/user/remote-access.md` pairing section](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/remote-access.md). For LUNA direct V1: QR and a manual URL/code path should terminate in the same validation/bootstrap operation; opening a URL alone must not silently trust or connect to an arbitrary host.

## Multiple machines and route selection

The registry loads persisted targets, groups routes by `environmentId`, drops unusable learned routes, retains a saved route with a missing profile so an actionable error can surface, and creates one supervised scope per environment. See [`EnvironmentRegistry.make` lines 207–274](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L207-L274) and [`createServiceScope` lines 360–397](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L360-L397). It starts every persisted environment with unbounded concurrency and only connects enabled entries in [`registry.ts` lines 480–495, 360–379](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L480-L495). Mobile presents a cross-environment workspace and manual per-draft environment selection; [`useWorkspaceState` lines 28–47](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/state/workspace.ts#L28-L47) combines catalog and shells, while [`NewTaskEnvironmentPickerRouteScreen` lines 205–257](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/threads/NewTaskContextPickerScreens.tsx#L205-L257) lets users choose a host. The user guide explicitly says mobile keeps manual environment selection while web/desktop have optional auto balance ([`remote-access.md`](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/remote-access.md)). LUNA should separate the selected host for a new task from the host ID attached permanently to an existing task; reselecting must not silently move a thread between machines.

Each environment has an ordered route list. The driver checks direct routes' public descriptor in parallel (2.5 s timeout) with no credential, then attempts routes in preferred order, temporarily skipping silent addresses and trying those last if necessary. It closes a failed route's half-open session before the next; an incompatible protocol stops the walk, while ordinary transient/blocked route failure can fall through. See [`driver.ts` lines 68–136, 144–185](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/driver.ts#L68-L136) ([preflight](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/driver.ts#L144-L199)). A successful connection is only published after the WebSocket session is ready and the initial config arrives. An answering public descriptor and then the WebSocket config are each checked for the expected environment ID ([resolver](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/resolver.ts#L291-L316), [session](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L294-L309)). This is the intended safety boundary for DHCP IP reuse and wrong-host routing, subject to the short descriptor-cache window below.

**Source caveat:** Bearer authorization's `verifyDirectEndpoint` caches a matching public descriptor for 10 seconds under expected environment ID and URL, then may reuse it without another fetch before requesting a bearer WebSocket ticket ([`authorization/service.ts` lines 90, 145–204](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/authorization/service.ts#L145-L204)). If an IP/URL changes owners inside that window, the source appears capable of sending the saved bearer to the new responder despite the earlier check. I did not reproduce this on a network, so classify it as a plausible short-window race, not a demonstrated exploit. The route preflight is public and credential-free, but a later actual attempt can take the cached authorization path. LUNA should revalidate host identity immediately before each credential-bearing request when address ownership can change, or bind the credential cryptographically to the intended host.

When connected through a lower-ranked route, a supervisor checks higher-ranked routes every 60 s and on relevant wakeups; its preflight includes authorization. A candidate that answered but failed the actual switch gets a 5-minute cooldown. See [`supervisor.ts` lines 40–54, 296–387, 608–627, 749–758](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L40-L54) ([route check](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L296-L387), [tick/wakeup](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L608-L627), [cooldown](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L749-L758)). The server's reported direct endpoints become learned routes; new reports replace stale learned LAN addresses but do not change user-saved addresses or their order, and learned routes borrow the parent route's credential. See [`registry.ts` lines 885–953](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L885-L953) and [`remote.md` lines 46–53](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L46-L53). A direct V1 with one route does not need this full ranking machinery, but it should model routes separately from host identity so LAN/tailnet/relay can be added without changing thread ownership.

Mobile's route detail UI shows order, address/type, **In use**, automatically found routes, current-session permissions, **Add route**, edit/reorder and removal; learned routes can be reordered but not removed. See [`EnvironmentRoutesSection.tsx` lines 47–96, 140–228, 285–323](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/settings/EnvironmentRoutesSection.tsx#L47-L96) ([actions](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/settings/EnvironmentRoutesSection.tsx#L140-L228), [badges](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/settings/EnvironmentRoutesSection.tsx#L285-L323)). Removing the last route removes the environment; sign-out drops only the relay route and preserves a host reachable another way. Turning a host off persists a disabled flag, drops its socket/retry loop while keeping registration/credentials/cache; retry is explicit. See [`registry.ts` lines 955–1085](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L955-L1085). The settings row shows status, error/trace ID, enable switch, URL/label editing for direct routes, reconnect and remove actions in [`ConnectionEnvironmentRow.tsx` lines 50–139, 151–255](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionEnvironmentRow.tsx#L50-L139) ([actions](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/connection/ConnectionEnvironmentRow.tsx#L151-L255)).

Editing the URL changes the first saved bearer route while retaining its credential; it normalizes syntax and saves before the next connection attempt verifies that the new address is the same environment. Other routes stay saved. See [`ConnectionOnboarding.updateBearerConnection` lines 169–255](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/onboarding.ts#L169-L255). Consequently, a successful **Save** is a successful local catalog update, not proof of reachability. LUNA should make that distinction visible if it offers URL editing.

## Persistence and offline presentation

The connection catalog, including route profiles, bearer credentials and relay DPoP access token records, is one schema-validated JSON document in Expo SecureStore. Reads and updates are serialized by an Effect semaphore; updates write SecureStore before replacing in-memory state. See [`catalog-store.ts` lines 16–42, 51–121](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/catalog-store.ts#L16-L42) ([serialized store](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/catalog-store.ts#L51-L121)), [`storage.ts` lines 51–157](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/storage.ts#L51-L157), and the actual SecureStore adapter in [`mobile-secure-storage.ts` lines 22–52](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/persistence/mobile-secure-storage.ts#L22-L52). A migrated legacy `t3code.connections` document maps relay entries without retaining their short-lived DPoP access token, and maps only bearer entries with nonempty token; migration writes the new catalog before deleting legacy storage. See [`migration.ts` lines 43–89](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/migration.ts#L43-L89), [`catalog-store.ts` lines 62–80](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/catalog-store.ts#L62-L80). A corrupt catalog is logged and discarded, then migration/empty fallback is attempted ([`catalog-store.ts` lines 83–104](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/catalog-store.ts#L83-L104)); the existing legacy mobile storage path also avoids persisting a transient DPoP token ([`lib/connection.ts` lines 19–34](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/lib/connection.ts#L19-L34)). LUNA should use secure storage for long-lived remote credentials and a schema/versioned migration path, and should not put bearer credentials in SQLite caches/logs.

Offline shell/thread/config/VCS-ref/favicons are separate per-environment SQLite cache records; connection catalog remains SecureStore. The database uses WAL and an exclusive schema transaction, `client_cache` keyed by `(environment_id, kind, cache_key)`, plus client preferences; it migrates older file caches and marks `user_version` only when migration completes. See [`mobile-database.ts` lines 9–25, 151–192, 252–335](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/persistence/mobile-database.ts#L9-L25) ([migration](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/persistence/mobile-database.ts#L151-L192), [schema/write](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/persistence/mobile-database.ts#L252-L335)). If SQLite cannot initialize, a service that fails cache operations is installed rather than pretending data persisted ([`mobile-database.ts` lines 424–446](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/persistence/mobile-database.ts#L424-L446)). Cache decode validates schema/ID and removes corrupt records; shell and thread saves are versioned in [`environment-cache-store.ts` lines 62–165](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/environment-cache-store.ts#L62-L165).

Shared shell state loads cached data immediately as `cached`, moves through `synchronizing`, then applies HTTP authoritative snapshot + WebSocket events into `live`; on disconnect it keeps data while downgrading status, and flushes latest live snapshot. It ignores old sequence numbers. See [`shell.ts` lines 42–91, 99–149, 183–249](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/shell.ts#L42-L91) ([persistence/disconnect](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/shell.ts#L99-L149), [sequence application](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/shell.ts#L183-L249)). After a *new* session it reloads HTTP shell snapshot before using a cursor; if HTTP refresh fails, it asks the socket for a full snapshot instead of trusting an incomplete cached cursor. On same-session foreground resubscription it can resume from in-memory sequence. See [`shell.ts` lines 325–411](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/shell.ts#L325-L411). Thread state has analogous cache/cursor handling and treats HTTP 404 as definitive deletion, clearing stale cache; an unavailable HTTP endpoint falls back to socket ([`threads.ts` lines 774–878](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/threads.ts#L774-L878)). The RPC client durable subscriptions switch to each new session and wait for replacement after transport loss ([`rpc/client.ts` lines 268–390](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/client.ts#L268-L390)). For LUNA, cached remote threads should be visibly stale/read-only until synchronized; cursor recovery must survive dropped sockets without duplicating or losing events, and a new session should establish authoritative state.

The initial server-config subscription is a session readiness gate; it reduces snapshot/theme/source events into a replay state and fans out through a bounded sliding PubSub. Subscribers joining late receive reconstructed current config plus later events, with revision-gap replay. A ping timeout gets a distinct "stopped responding" error and an ending config subscription closes the session. See [`rpc/session.ts` lines 171–225, 230–399](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L171-L225) ([subscription/replay](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L230-L399)). LUNA direct V1 should have a small explicit initial snapshot/readiness contract before declaring the host connected, even if it does not copy T3's Effect implementation.

## Network changes, backgrounding, retries, and compatibility

Mobile uses Expo Network for initial online/offline/unknown and change events. On foreground it rechecks current status. A separate network-path watcher compares Wi-Fi/cellular type and signals `network-changed` even if both are online; the first type is seeded to catch the first transition. See [`platform.ts` lines 33–122](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L33-L122). `AppState` sends an active wakeup; under 10 seconds background => fast probe, 10 seconds or more => immediate session replacement. Cloud account changes also wake connection handling. See [`platform.ts` lines 124–155](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L124-L155), [`app-state-wakeups.ts` lines 3–18](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/app-state-wakeups.ts#L3-L18). A separate activity reporter updates server leases every 25 s with 45 s TTL, app visibility/state and observed background scopes; this is presence/reporting, not guaranteed background socket liveness ([`background-activity.ts` lines 26–87, 89–116](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/background-activity.ts#L26-L87), [subscriptions](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/background-activity.ts#L89-L116)).

The supervisor's connected state probes on short return, network path change, retry, and even an offline report instead of killing a healthy socket. It uses a 3 s quick probe for mobile resume/path change and a 15 s default probe; long return replaces the session immediately because iOS/Android may suspend and kill sockets without close events. A failed/timeout probe reconnects immediately once, then normal backoff applies. See [`supervisor.ts` lines 533–676, 867–986](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L533-L676) ([retry state](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L867-L986)). Retry jitter begins under 2 seconds and caps at 5 minutes; a stable 30-second session resets the ladder. These constants are at [`supervisor.ts` lines 40–54, 134–145](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L40-L54). The server's `connectionProbe` capability chooses a dedicated probe RPC, with `serverGetConfig` fallback for older hosts ([`rpc/session.ts` lines 374–382](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L374-L382)). LUNA direct V1 needs lifecycle revalidation, bounded retry with jitter, and a user-triggered retry; no phone should be reported "connected" solely because an old socket object exists.

Protocol negotiation is explicit. A missing server descriptor protocol version is treated as version 1; a mismatched client/server protocol blocks, and an older host advertises a remote update affordance only if its capabilities support it. The client appends the current orchestration protocol version to the socket URL. See [`compatibility.ts` lines 9–42](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/compatibility.ts#L9-L42), used before opening the session in [`resolver.ts` lines 306–320](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/resolver.ts#L306-L320). Some individual RPC behavior is also capability-gated by the server config, for example probe, shell/thread resume markers and theme/usage streams ([`rpc/session.ts` lines 249–261, 374–379](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L249-L261), [`shell.ts` lines 335–341](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/shell.ts#L335-L341)). For LUNA, stable V1 wire version and server capability flags should be in the pre-auth/public descriptor and first authenticated config, with clear update messaging for app/host skew.

## LUNA direct V1 implications and credible failure modes

Suggested minimum, derived from T3's source rather than a claim about LUNA's current implementation (another lane must verify LUNA gaps):

1. Durable host ID and public descriptor, plus identity verification before credential use and again after opening the authenticated stream. Failure: a previously paired Wi-Fi IP now belongs to another laptop.
2. User-mediated QR and manual URL/code pairing, one-time code redemption into a device credential, secure persistence, clear revocation/unpair semantics. Failure: camera denial, malformed QR, expired/spent code, or a wrong-machine route must not save partial credentials.
3. One per-host connection supervisor and statuses: available/disabled, offline, connecting, connected, retrying with reason, blocked/incompatible. Failure: a dropped socket silently appears live or credentials changed while old cloud session persists.
4. Initial snapshot/readiness gate, durable event subscription with cursor/reload strategy, per-host cache labelled stale while offline, explicit reconciliation after reconnect. Failure: missed events while backgrounded, cached cursor falsely marking partial data complete, duplicate updates, stale deleted thread.
5. App lifecycle signals for foreground and Wi-Fi/cellular path changes; short resume probe and long resume replacement; bounded jittered retry and manual retry. Failure: OS silently kills suspended socket, network switches while still "online", or rapid retry drains phone/host battery.
6. Stable environment selection for new tasks across multiple saved hosts, while existing tasks stay tied to the host that owns them. Future route list can include LAN/tailnet/relay, but direct V1 may start with one user-saved route per host. Failure: new task starts on unintended host; same host paired at another address appears twice; deleting a route deletes a machine unexpectedly.
7. Capability/version handshake and visible upgrade state. Failure: mobile update tries a newer RPC against an older host and loops reconnecting forever.

Proposed **real-boundary E2E** scenarios for LUNA (these are proposed, not executed T3 tests):

- Start an actual LUNA host and phone app; pair via displayed QR, close/relaunch phone, and verify authenticated reconnection to the same durable host ID without reusing the one-time code. Repeat by manually entering address/code. Preserve an artifact containing the host descriptor ID, redacted connection phases, phone screen recording, and event/cursor trace.
- Connect phone over Wi-Fi, open a real thread, switch to cellular/Tailscale while host remains reachable, then background >10 s and foreground. Verify transition through revalidation to live state, no duplicate/missing thread events, and one active session after recovery. Preserve a timed network/phase/sequence trace and screen recording.
- Pair two hosts with distinct IDs but same project path/name. Create a task on host B, reload offline cache and reconnect; verify that task never appears under host A or moves when selecting A for a new task. Artifact: host IDs, thread IDs, command receipts and phone UI capture.
- Reassign a saved IP to a different test host, including less than 10 seconds after a successful descriptor check. Verify public descriptor mismatch blocks sending the LUNA credential and explains why the route is unusable; correct address and reconnect. Artifact: scrubbed HTTP request/descriptor log proving no Authorization header went to the wrong host. This is a desired LUNA guarantee and a targeted check for the T3 source caveat above, not a claim that T3 passes it.
- Update phone build to a deliberately incompatible test host protocol; verify an actionable unsupported state without endless retries, then update host and reconnect. Artifact: version/capability descriptors, state trace, UI capture.
- Kill the host during an active stream, inspect cached thread as stale, restart host with an intervening event and a deleted thread, then verify authoritative reconciliation and final sequence. Artifact: server event log and persisted phone cache readback (without secrets).
