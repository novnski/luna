# LUNA iOS/mobile parity audit against T3 Code remote

**Audited source:** LUNA `4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c`; T3 Code snapshot `a8bdfdb54181fb5c9d43f2747112c137a804d016`. Read-only static source review on 11 October 2026. No build, simulator, physical phone, configured edge, direct Mac route, or running provider was exercised. Treat `source-backed` below as reachable code path, not live behavior proof. LUNA source links use the audited commit; T3 links use the supplied immutable snapshot commit. This lane inspected production source, project guidance, and plans, **not existing tests**.

## Result in one sentence

LUNA has a source-visible SwiftUI *hosted-edge peer* app for project sessions and conversation control, but its current root has only cloud WorkOS, dev-edge, and demo entry points; a paired, direct, profile-scoped Mac has no iOS route or transport. T3's mobile stack exposes an environment-centric remote product with connection management plus many host-powered screens absent from LUNA iOS. [LUNA root](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/LunaApp.swift#L38-L53), [LUNA sign-in](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Views/SignInView.swift#L102-L141), [T3 mobile routes](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/Stack.tsx#L208-L279).

## Existing LUNA phone topology, checked UI → wire → host/policy

1. `RootView` renders sign-in, org picker, or `HomeView`; the actual `HomeView.Route` enum contains only space, chat, and new-session routes. Home's person menu contains Demo mode text and Sign out. There is no reachable connection/enrollment/settings route in this tree. [Root](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/LunaApp.swift#L38-L53), [Home route and destinations](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Views/HomeView.swift#L8-L57), [Home toolbar](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Views/HomeView.swift#L105-L120).
2. WorkOS `ASWebAuthenticationSession` sends an authorization code to `/auth/exchange`; the client then scopes to an organization through `/auth/refresh`, stores access/refresh tokens in Keychain, and creates `AppConfig(edgeURL, userId, orgId, deviceId)`. This is cloud account enrollment, not Mac pairing. The app bundle must contain `LUNA_EDGE_URL` and `LUNA_WORKOS_CLIENT_ID`; otherwise sign-in says sync is unconfigured. A dev-edge bearer and demo dataset are separate developer/demo modes. [Sign-in](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Views/SignInView.swift#L11-L35), [user action](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Views/SignInView.swift#L102-L141), [model connect](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/AppModel.swift#L196-L274), [README configuration](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/README.md#L17-L49).
3. The normal data plane dials `registry/{org}/ws` and `chat2/{chat}/ws` at the edge, with HTTP row/checkpoint fallbacks. The host-only RPC data path dials edge `device/{device}/ws` as role `client`, authenticating with the edge token; the edge relays binary frames carrying `ControlRpc` JSON. The phone's chat command ledger writes `run`, `steer`, `interrupt`, and `respondInput`, then POSTs `/device/{host}/nudge`. No current path reads a QR-issued Mac session or connects to a LAN/public Mac HTTPS endpoint. [AppConfig registry/chat2](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/AppConfig.swift#L105-L175), [relay connect](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Sync/DeviceRelayClient.swift#L214-L260), [command enqueue and nudge](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Sync/SessionStore.swift#L619-L661), [nudge endpoint](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/AppConfig.swift#L204-L225).
4. Mac `RemoteAuthStore` and per-connection `RemoteRpcService` are real desktop foundations, but the latter's current method policy gives only `environment-read`, `tasks-read`, `files-read`, and `terminal-operate`. It denies all other known methods locally; therefore a new direct phone cannot obtain task mutation simply by calling an existing method over that adapter. Scope and per-command admission must be designed together. The existing plan also identifies the direct gateway, TLS, iOS transport and scanner as proposed work. [Mac remote policy](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/crates/rpc/src/remote_auth.rs#L398-L535), [proposed component map](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/implementation-plan.md#L25-L38). This is especially important because old edge device-room peer trust and new paired-principal trust are different boundaries.
5. Existing `Control this Mac` plan is explicitly **pending** and specifies direct-only V1 (no relay, hosted identity, VPS or synced transcript service), with the Mac as execution owner. Its feature inventory is a seed and explicitly calls for this exhaustive source review before M0. Its existing E2E list is future acceptance, not evidence of passed tests. [scope](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/README.md#L1-L15), [inventory caveat](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/feature-parity.md#L1-L19), [validation caveat](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/validation-plan.md#L1-L11).

## Specific discrepancies and cautions for the pending plan

- The existing parity seed RC10 says “questions and approvals” for M3; only questions have a current phone UI. The direct implementation needs approval projection and action from scratch, plus authoritative host policy. The existing iOS `autoApprove` field must not be mistaken for effective Full/Auto permission; current proto explicitly says legacy sandbox/auto-approve are backward compatibility and canonical mode is separate. [iOS request](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Models/Entities.swift#L344-L370), [proto](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/crates/proto/src/agent.rs#L129-L165), [seed](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/feature-parity.md#L23-L35).
- The first direct release must be honest about parity. Existing iOS feature code can inform native UI, but its queue protocol, row creation, edge bearer and cached org docs cannot be reused as direct-host authorization. A new host gateway cannot simply expose local IPC; `RemoteRpcService` currently rejects all task mutations. [relay and bearer](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/Sync/DeviceRelayClient.swift#L214-L260), [policy](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/crates/rpc/src/remote_auth.rs#L417-L535).
- T3's route count should be used as inventory, not a demand to clone every feature into direct V1. User's existing `Control this Mac` decision is a single paired Mac with direct transport, while T3 also supports cloud T3 Connect, multiple routes and multi-environment management. [LUNA decision](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/docs/pending-tasks/control-this-mac/README.md#L3-L9), [T3 route guide](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/remote-access.md#L10-L34).
- Some existing iOS features are host-version/capability gated. `listHarnesses` and `listModels` silently fall back to static catalogs on unreachable host; queue and attachment choices depend on advertised device capabilities/version. A direct client should expose capability uncertainty to the user and fail closed on operations whose behavior could change. [catalog fallback](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/AppModel.swift#L360-L386), [queue gates](https://github.com/novnski/luna/blob/4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c/apps/ios/Luna/App/AppModel.swift#L680-L719).

## E2E scenarios to add or sharpen in the parent pending docs

1. Pair a *local-only* Mac profile from a physical iPhone on LAN, then inspect Mac authority roster and authenticated identity. Scan an expired/wrong-profile QR and ensure no saved usable host. Repeat with camera denied and manual import. Evidence: masked screen capture, host process/port/TLS fingerprint and command receipt. This complements existing E02 rather than claiming it passed.
2. Create one project-bound task from phone and compare Mac/phone project ID, task ID, selected provider/model, requested and **effective** permission mode; run a deterministic provider request. Interleave a second phone and desktop edit to prove one host owns acceptance.
3. During a streaming run, queue with an image, edit under lease, reorder, send now or steer according to host capability, stop, then answer a question and an approval. Inject stale turn/request IDs; verify explicit reject and no extra provider action. Existing iOS question path is only a starting UI reference.
4. Lose the socket after the host accepts a command but before the phone receives the reply. Reconnect over the same paired identity and request ID, retrieve one receipt, see one transcript user message and one execution. Repeat across app suspension and Mac restart, with a revoked phone failing immediately.
5. Open exact task checkout file, image and diff; try symlink traversal and a switched checkout. Terminal and browser/device preview are separate later journeys with separate grants, never implied by a successful file read.
6. Wi-Fi off/cellular on from outside the LAN: record actual route and authenticated task identity. If no inbound route exists, mark direct WAN acceptance blocked with precise diagnosis; do not substitute T3 Connect/Tailscale/cloud relay. This preserves the previously stated V1 product boundary.
