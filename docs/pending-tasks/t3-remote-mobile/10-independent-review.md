## High-impact completeness checks for the pending docs

1. Every feature row should say *source implementation*, *live observed*, or *proposed*; source route registrations alone do not prove store release or runtime success. T3 2.0.0 source and current stable listing are on different version lines.
2. Transport diagram must distinguish direct LAN/public/Tailscale/SSH/Connect, route ordering and learned routes, environment identity, authentication, and the host-owned execution boundary.
3. Pairing grant lifecycle needs one-time expiry, issue-only secret display, route-scoped session state, re-pairing to change scopes, revoke session vs cancel link, and no raw token in screenshots/logs/URL query to a hosted origin. T3 `docs/internals/remote.md:58-69` puts hosted pairing secret in a URL fragment.
4. LUNA parity gap must distinguish existing phone UI/doc sync, remote RPC read-only plus terminal scopes, headless SSH-forwarded loopback listener, and *headed direct host* still pending. Describe real task control as missing until admission and physical-device E2E pass.
5. Existing LUNA `control-this-mac` pending package already owns V1 constraints. New research should amend/link it, not create conflicting architecture or imply T3 Cloudflare tunnel is accepted for V1.

## Open verification questions

- Is there any alternate current LUNA iOS code path that calls `EXECUTE_TASK_COMMAND` through an authenticated host? The targeted `SessionStore.swift` path does not; future docs should avoid whole-app negative claims without a full route inventory.

- For T3 direct plain HTTP on LAN, is there a platform-specific protection or accepted risk beyond server auth? Do not import this detail into LUNA; its approved plan requires pinned TLS.
- For T3 Connect, the Worker does not proxy ordinary app traffic, but Cloudflare's managed tunnel infrastructure does carry it. Use precise language about each component.
