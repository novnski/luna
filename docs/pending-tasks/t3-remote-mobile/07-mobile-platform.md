## Exact activity notification route

1. The environment server emits per-thread activity only when publication is enabled and relay link credentials exist. It signs a proof and posts the state to `publishAgentActivity`; current active threads are published as a catch-up snapshot after linking ([server relay L445–521](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/relay/AgentAwarenessRelay.ts#L445-L521), [L735–776](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/relay/AgentAwarenessRelay.ts#L735-L776)). Thus this push path requires a linked environment and a running host publisher; a remote UI connection alone is insufficient.
2. The relay verifies that the principal owns the environment and checks the publish signature before accepting state ([relay API L1173–1193](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/http/Api.ts#L1173-L1193)). It persists active/terminal rows, aggregates for linked users, and fans out by registered device platform: FCM for Android; APNs Live Activity plus alert paths for iOS ([publisher L57–108](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/agentActivity/AgentActivityPublisher.ts#L57-L108), [L145–190](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/agentActivity/AgentActivityPublisher.ts#L145-L190)). APNs jobs and FCM jobs are queued and retried in relay code; the relay uses APNs credentials and optional FCM service account ([relay README L15–40](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/README.md#L15-L40), [L139–156](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/README.md#L139-L156)). This is a *side channel* for awareness; normal remote API/WebSocket traffic goes directly between phone and environment after connection ([relay README L6–12](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/README.md#L6-L12)).
3. The phone requests OS notification permission, creating Android’s high-importance `agent-alerts` channel or requesting iOS alert/badge/sound ([permissions L33–77](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/notificationPermissions.ts#L33-L77)). It obtains a *native device* push token through `expo-notifications`, not an Expo push token, then registers a stable device ID, account, platform, token, app/bundle and APNs sandbox-vs-production environment with the relay ([registration L269–307](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/remoteRegistration.ts#L269-L307), [L729–799](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/remoteRegistration.ts#L729-L799), [payload L6–51](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/registrationPayload.ts#L6-L51)). Relay mobile registration and unregistration require signed-in user token plus `mobile:registration` DPoP scope/proof ([relay API L763–808](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/http/Api.ts#L763-L808)). The relay claims reused tokens away from old rows and upserts the device with its preferences ([Devices L88–165](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/agentActivity/Devices.ts#L88-L165)).
4. Token rotation triggers re-registration; foreground return re-registers/reconciles activity state. Successful matching registration is cached per account and relay URL; sign-out calls relay unregister, clears native Android presentation and ends local iOS Live Activities. The client logs an unregistration error rather than guaranteeing remote deletion if sign-out is offline ([registration L381–449](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/remoteRegistration.ts#L381-L449), [L810–849](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/remoteRegistration.ts#L810-L849), [L945–967](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/remoteRegistration.ts#L945-L967), [cloud auth L89–108](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/cloud/CloudAuthProvider.tsx#L89-L108)). Relay unregistration deletes activity and device rows scoped by user ID/device ID ([Devices L178–210](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/agentActivity/Devices.ts#L178-L210)).
5. Notification taps are navigation, not an approve/respond command. The app validates `/threads/:environment/:thread` links, rejects query/fragment and malformed forms, deduplicates response IDs, and handles both live and cold-start responses ([payload L37–119](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/notificationPayload.ts#L37-L119), [navigation L10–53](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/features/agent-awareness/notificationNavigation.ts#L10-L53)). No badge count policy or direct notification approval action is established by this code.

## Product and infrastructure implications for Luna

1. **Baseline remote mobile app.** A connected phone needs an authenticated, scoped environment/session catalog and an API/WebSocket client; notification infrastructure does not carry the actual chat/control traffic. The host and mobile app must share stable environment/thread IDs for navigation. Build this before push UX. The parent’s connection/transport lanes should own the precise Luna gap judgment.
2. **Awareness service.** For push parity, define a narrow server activity projection (running, awaiting approval/input, complete, failed, deletion), publish it only after state commits, persist latest aggregate and terminal TTL, and fan out by linked account and device. Use separate authorization for host publishing and phone registration, verify per-environment ownership, and support token rotation/unregister. T3’s publish proof and relay API demonstrate those boundaries ([server L474–513](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/relay/AgentAwarenessRelay.ts#L474-L513), [relay API L763–808](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/http/Api.ts#L763-L808), [L1173–1193](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/src/http/Api.ts#L1173-L1193)).
3. **Presentation sequence.** Start with permission-aware push alerts and validated tap-to-thread links. Treat iOS Live Activity as opt-in, foreground-armed and APNs-updated; Android ongoing notification requires its own native FCM receiver and expiry/dismiss logic. Do not promise an iOS Live Activity appearing while the app has never been opened/armed. Keep badge policy explicit; T3 does not set foreground badges. Include notification registration status in settings so “relay linked” is not mistaken for “phone receives push.”
4. **Owned release services.** Luna needs its own Apple developer team, bundle IDs, App Groups/share extension, push entitlements, associated domains, APNs key and topic; Google Play package, Firebase project/`google-services.json`, FCM service account; mobile auth provider/issuer, relay hostname, signing keys, persistence and queue/worker operation, observability; store accounts and review; and OTA project/channel ownership. T3’s T3 Tools team/IDs and Expo project cannot be reused ([app config L248–265](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/app.config.ts#L248-L265), [L299–304](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/app.config.ts#L299-L304), [EAS L60–90](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/eas.json#L60-L90), [relay README L79–96](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/README.md#L79-L96), [L139–156](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/infra/relay/README.md#L139-L156)). Personal Team test builds deliberately lose push, widget and share extension capabilities ([mobile README L69–71](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/README.md#L69-L71)); this affects parity QA.
5. **Verification gates.** Test signed iOS and Android binaries with real APNs/FCM tokens and an independently reachable host: cold start, foreground/current-thread suppression, app background/terminated, permission denied, push token rotation, account switch, environment unlink, host offline, APNs sandbox vs production, Android notification promotion/expiry, Live Activity arm/update/end, remote delivery retry, shared media cold start, OTA with pending draft. Preserve evidence as versioned build number, device/OS, relay delivery ID and host thread ID. Static source cannot prove these operational paths or store-binary feature coverage.

## Open points to avoid overclaiming

- No device test of current store binaries or exact iOS/Android feature parity occurred in this lane.
- The current source has a generic `voiceTranscription.ts` fallback returning null, so Android voice dictation should be marked unsupported/unproven until another Android transcriber or runtime path is demonstrated.
- No direct approval/answer action was found in the inspected notification handlers; tapping routes to thread UI. An exhaustive action audit would need all payload producers and installed binary inspection.
- iPad `supportsTablet` and UI code do not establish full tablet route/layout quality.
- A failed offline sign-out may leave relay device registration until subsequent server-side cleanup; determine actual expiry/reconciliation behavior before adopting the pattern.
