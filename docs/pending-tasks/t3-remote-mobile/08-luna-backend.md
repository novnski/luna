# Lane 8 — LUNA remote backend, audited against the T3 mobile-host shape

Source cut: LUNA `4f3a6b0cbe2603db7b18f7d452d3a5dfdecb183c` and T3 `a8bdfdb54181fb5c9d43f2747112c137a804d016` (the provided immutable snapshot). This is a read-only source review, not a live phone, Mac, WAN, or deployed-relay test. LUNA line references below use repository-relative paths at that SHA; T3 links use the pinned SHA. Existing `docs/pending-tasks/control-this-mac/` is a **proposal** (its README explicitly says the host and mobile migration were not implemented by that task, lines 1–9). Its direct-only, no-relay V1 requirement remains the product constraint even though LUNA also has older optional cloud and SSH infrastructure. The T3 material below is used as a contract comparison, not a recommendation to adopt its Connect relay.

## Verified runtime boundaries

1. **Local owner is a separate trust domain.** Headed LUNA boots/attaches to an engine through loopback IPC (`crates/ui/src/state.rs:480–568`); `serve_ipc` binds `127.0.0.1` and wraps the service with local-owner IPC authority (`crates/engine/src/lib.rs:1600–1615`). The WebSocket acceptor rejects any `Origin` header, specifically to keep ordinary browser pages from dialing this local socket (`crates/rpc/src/server.rs:174–203`). The headed bootstrap call site starts *only* that IPC listener, not `remote_rpc_factory` (`crates/ui/src/state.rs:547–568`). Do not publish/forward that socket as the phone API.
2. **Paired remote authority exists as a bounded foundation.** `RemoteAuthStore` is profile-specific and stores SHA-256 hashes of random 256-bit pairing/session credentials in private `remote-auth.json`; incompatible environment/protocol and damaged/unsafe storage fail closed (`crates/rpc/src/remote_auth.rs:160–201`, `crates/engine/src/lib.rs:509–531`). It issues a short-lived, single-use pairing; redemption persists a distinct expiring session; session revocation is available (`crates/rpc/src/remote_auth.rs:242–359`). Pairing/session target includes machine ID, workspace scope, environment ID, protocol version and capability (`crates/rpc/src/remote_auth.rs:22–52`, `208–240`). Existing `RemoteScope` values are only `environment-read`, `tasks-read`, `files-read`, `terminal-operate` (`crates/rpc/src/remote_auth.rs:27–34`). The local CLI prints a credential once and can list/revoke pairings and sessions (`apps/luna/src/remote_cli.rs:22–42`, `64–155`). No stable paired-phone roster, last-authenticated connection, grouping of sessions under a device, global remote-enable gate, QR, direct endpoint or TLS trust is present in those concrete types/call sites.
3. **A remote connection gets its own guard; it is not a local owner.** `remote_rpc_factory` constructs one `RemoteRpcService` per socket (`crates/engine/src/lib.rs:872–893`). On that guard, pairing redemption and session authentication precede methods; each call checks expiry/revocation and its method scope, denies mismatched `targetDeviceId`, and rechecks values/streams (`crates/rpc/src/remote_auth.rs:398–487`). Unknown methods fail closed. Crucially, it passes plain `method, params` into `EngineRpc` (`remote_auth.rs:452`): the authenticated session principal is **not** carried as a typed engine context. Existing task-command payloads accept client-provided `actorId`, `clientId`, and `clientSessionId` (`crates/engine/src/rpc.rs:289–309`), so adding task mutation to the method allowlist alone would admit caller-supplied attribution. Make the principal and allowed intent/target an engine input, with host-derived actor fields.
4. **Remote method policy currently allows reads and terminal control but denies task work.** The explicit method map permits engine catalog reads; selected task work/identity/receipt/message/queue watches; repositories, workspace files/images, diffs, and terminal inventory; plus open/subscribe/write/resize/close terminal (`crates/rpc/src/remote_auth.rs:490–535`). `EXECUTE_TASK_COMMAND`, `QUEUE_MESSAGE`, `STOP_TASK_WORK`, broad `WATCH_CHATS`/`WATCH_SPACES`, `WRITE_WORKSPACE_FILE`, preview streams and auth/backup/settings operations are absent from the permitted arms and therefore local-only by the final inventory branch. The engine does implement `EXECUTE_TASK_COMMAND` locally (`crates/engine/src/rpc.rs:10361–10396`) and its intent enum includes create, send/steer/stop, approval/question responses, queue operations and many sensitive variants (`rpc.rs:337–407`, `610–660`). This is a substantial reusable admission engine, not remotely authorized operation.
5. **Durable command receipts already offer the right settlement shape.** The wire receipt records command ID, task, payload hash, status, revision/sequence, binding generation, active turn, actor/client identity and timing (`crates/proto/src/task_command.rs:29–143`). Engine admission creates a pending receipt under a per-task gate; duplicate ID can return prior receipt, changed hash conflicts, and revision/binding/turn preconditions are checked (`crates/engine/src/rpc.rs:3000–3204`, `3313–3351`). A provider call can remain pending/unknown rather than being falsely reported applied (`rpc.rs:3503–3600`). The owner doc drain requires an exact local persisted executable-row record; it rejects forged/replayed synced command rows regardless of `issued_by` (`crates/engine/src/doc_host.rs:7160–7240`). Queue drain similarly marks an unadmitted head for local review (`doc_host.rs:6010–6075`). A direct phone should call this host-owned admission path; it cannot gain authority by editing Loro rows or writing to a synced room.
6. **Headless SSH direct access is real but narrow.** `luna-headless` requires distinct IPC and guarded remote ports (`apps/luna-headless/src/main.rs:16–27`, `150–157`); engine binds the guarded remote port on `127.0.0.1` and installs `remote_rpc_factory` (`crates/engine/src/lib.rs:1490–1523`). `luna ssh` uses the system SSH host key and forwards that guarded port; its user-facing window is a bounded read-only task view, not a full conversation client (`docs/direct-remote-ssh.md:1–3`, `29–37`). A packaged-binary integration test drives unauthenticated rejection, one-time redemption, authentication and exact engine identity (`apps/luna-headless/tests/startup.rs:62–132`), but neither that test nor fake SSH proves physical second-host/phone access. This does not supply the headed Mac's LAN HTTPS listener or iPhone onboarding.
7. **Optional Edge mesh/relay is a distinct path.** For a synced profile or an explicitly configured development bearer, engine assembly enables Edge networking; local-only mode does not (`crates/engine/src/lib.rs:1279–1309`). It starts a DeviceRoom host relay and peer cache through Edge (`lib.rs:1377–1399`; `crates/rpc/src/device_room.rs:1–16`, `306–400`). Each virtual relay connection gets a `RemoteRpcService`, and unauthenticated legacy nudges are ignored (`device_room.rs:438–466`, `571–584`). The peer link requires an explicit paired `remote_session` before dial and authenticates on connection (`device_room.rs:757–797`, `1039–1091`). The normal `Engine::assemble_runtime` setup does not populate that source (`lib.rs:1377–1394`), and the only assignments found by a repo-wide `rg 'remote_session\s*=' crates apps --glob '*.rs'` are in tests. Thus the outbound desktop peer cache has a configuration seam but no normal profile-backed device-session source. Do not count a registry heartbeat or Edge route as a successful authenticated remote client. The separate `luna-relay` binary is an optional managed tunnel/route implementation (`apps/luna-relay/src/server.rs:172–226`, `apps/luna-relay/src/tunnel.rs:377–408`); it remains outside direct-only V1.
8. **Files, terminal and preview need careful separation.** Current file RPCs enforce a workspace target owned by this device and bounded relative paths, disallowing `.`/`..` and `.git` (`crates/engine/src/workspace_files.rs:1–4`, `29–42`, `116–175`, `221–318`). The `files-read` grant is still profile-wide at the method layer; no pairing-specific project grant is checked in `RemoteRpcService` (`remote_auth.rs:432–452`). Terminal operation is powerful: `OPEN_TERMINAL` takes a chat ID, but if no chat/cwd exists the engine falls back to the user's home directory, then opens the login shell (`crates/engine/src/rpc.rs:12280–12295`; `crates/engine/src/terminals.rs:209–244`, `299–335`). `WRITE_TERMINAL` uses only terminal ID (`rpc.rs:12310–12315`), not a per-remote-session owner. Do not put `terminal-operate` in the default phone grant; before richer phone terminal use, bind it to a verified task/workspace and session ownership. Preview is a different service: local proxy plus optional Edge-signaled WebRTC peers, with HTTP bytes on DataChannel rather than Edge (`crates/preview/src/lib.rs:1–12`, `signaling.rs:58–84`, `peer.rs:1–2`; `crates/engine/src/lib.rs:1332–1348`). There is no guarded remote-RPC preview allowance in `remote_auth.rs:490–535`, and the local-only profile supplies no Edge signaling. Treat remote phone browser/preview as a separate direct-host contract.
9. **Mac lifecycle controls are partial.** Existing power assertion is process-local and tied to one selected actively working local task (`crates/ui/src/power.rs:1–60`, `119–146`); Settings says that explicitly (`crates/ui/src/settings/general.rs:173–177`). `Settings → Devices` describes registry presence and rename, not paired authority (`crates/ui/src/settings/devices.rs:1–7`, `54–61`, `70–95`). Repository-wide source search found no `Control this Mac`, `Allow connections`, or remote auth references in UI/iOS code. It cannot be inferred from the pending-task mock/screenshot. Host-on/host-off, paired-device status, last authenticated use, external-power wake reason, route readiness, and transport-triggered reconnect are new work. Existing headless daemon lifecycle (`apps/luna/src/main.rs:37–73`) is not a substitute for hosting from the already-running headed engine.

## T3 contrast that matters for architecture

T3's mobile runtime exchanges a pairing/bootstrap credential for a bearer or DPoP access token through the environment's `/oauth/token`, checks `/api/auth/session`, and requests a short-lived `/api/auth/websocket-ticket` before `/ws`; it sends client surface, version and connection-method metadata on socket setup ([`packages/client-runtime/src/authorization/remote.ts` at a8bdfdb](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/authorization/remote.ts#L25-L83), [token and ticket calls](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/authorization/remote.ts#L86-L223)). Its server defaults to a local bind but can use an explicitly configured host (`apps/server/src/server.ts:276–299`); a headless serve path derives a reachable address and prints a pairing URL/QR (`apps/server/src/startupAccess.ts:45–98,122–147`). These concrete behaviors show the missing LUNA layers: phone-readable bootstrap, a transport/session handshake, a reconnectable client projection, and host connection metadata. T3's available cloudflared layer (`apps/server/src/server.ts:275–281`) should **not** be imported as a V1 route; the LUNA pending plan expressly requires direct LAN/public routing without relay (`docs/pending-tasks/control-this-mac/README.md:5–9,72–85`). T3's raw headless HTTP pairing URL is also not a safe TLS-pinned design for LUNA's direct phone product. Defer exact T3 screen/feature parity to the dedicated mobile research lanes rather than inferring it from backend modules.

## Implementation packages and acceptance probes

1. **Authority model and threat/failure inventory first.** Add paired-device identity/grouping, approved scopes, connection metadata, session-to-device relationship, last authenticated use, remote-enable generation, local admin RPCs, migrations and permission hardening. Decide product session expiry. Failure probes: same-label phones do not merge; revoke all device sessions/pending grants before connection teardown; old profile/backup cannot resurrect access; damaged/unsafe store leaves local engine usable. Keep current headless SSH scopes working on purpose.
2. **Direct headed host vertical slice.** Add an owned TLS/HTTPS + WebSocket listener inside the headed engine runtime, separate from IPC. Bind an explicit unprivileged port; use a fresh `RemoteRpcService` per socket. QR trust carries pin/target/endpoints; native iPhone connects on LAN with verified trust and Keychain credential. Failure probes: disabled at first launch, occupied port, wrong pin/target, profile switch, phone LAN permission, silent disconnect, disable mid-call, no accidental owner-IPC route. Retain exact process/port/certificate/route evidence.
3. **Remote read projection.** Supply bounded host-owned project/task catalog and consistent transcript/status/queue/receipt snapshot, then incremental stream with cursor or resnapshot semantics. Scope data by paired profile and optional project grant. Failure probes: snapshot/event race, duplicate/gapped events, stale stream after reconnect, slow consumer/large tool body, different paired Mac showing stale cache as current. A live engine/provider fixture should prove task IDs and transcript agree between desktop and phone.
4. **Command admission and interaction control.** Introduce a typed remote principal to engine dispatch, never from caller JSON; allow only reviewed intent variants under `tasks-operate`/`interactions-respond`. Bind actor/device, target task/project/workspace, command ID, payload hash, expected revision/binding/turn and current provider capability. Use existing receipts and local executable admission. Failure probes: client-attributed spoofing, forbidden nested intent, receipt lost after accepted action, repeat same ID versus altered payload, stale turn/approval, synced-row forgery, phone revoked while accepted work continues by host policy. The existing `ExecuteTaskCommand` cannot be opened wholesale.
5. **Files, attachments, terminal and preview as separate grants.** Keep existing safe relative-path resolution, add explicit remote project/artifact selection and lazy bounded body delivery. Add task-bound upload staging/hash/cleanup before image attachments. Leave terminal off default pairing and require verified task and session ownership before expanding mobile terminal; avoid the current home fallback in a remote path. Add direct preview only with explicit service/target access and no generic local proxy exposure. Failure probes: traversal/symlink, cross-task attachment reference, huge file/tool output, terminal ID guessed from another session, preview service acting as open proxy.
6. **Lifecycle/readiness and release proof.** Add Settings → Connections host controls and a shared power coordinator with an external-power remote reason. Show three independent states: listener ready, phone authenticated, and route actually proven. Exercise physical iPhone LAN and cellular with Wi-Fi/VPN off where a direct route exists; inspect destination and certificate, not only DNS/QR. If ISP/NAT prevents the route, record that WAN acceptance is blocked and ship an honest LAN limitation rather than activating a relay. Use the existing E01–E15 scenarios in `docs/pending-tasks/control-this-mac/validation-plan.md:68–88`, with retained sanitized logs, command receipts and screenshot/video hashes as that plan requires (`validation-plan.md:5–11`).

## Documentation corrections to preserve during synthesis

* Keep `control-this-mac` labeled pending; it is more detailed than the implemented code and must not be used as a completion report (`README.md:1–9`; `implementation-plan.md:1–3`).
* State that LUNA has **three different remote mechanisms** with different authority: optional synced Edge DeviceRoom/preview signaling, authenticated loopback RPC behind SSH for a headless host, and the still-unbuilt direct phone gateway. QR pairing by itself creates trust material, not a network route.
* Refine the current plan's vague “terminal operations exist” language with the concrete home-directory fallback and terminal-ID-only write path; those are serious scope choices before granting phones a shell.
* The current direct plan's proposed `remote-direct-v1`, task-control and interaction capabilities are sound as negotiation targets. They are **not** current `remote-auth-v1` features.
