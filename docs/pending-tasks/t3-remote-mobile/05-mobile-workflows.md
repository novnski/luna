# T3 Code mobile workflows and reachability audit

Source snapshot: `pingdotgg/t3code` at `a8bdfdb54181fb5c9d43f2747112c137a804d016` (SHA supplied with the snapshot; this extracted directory has no `.git`). Inspection date: 2026-10-11. I read repository `AGENTS.md`, `apps/mobile/package.json`, the actual native route table, mobile screens/actions, shared client commands, RPC authorization, and representative server handlers. This is a **static source audit**. I did not launch an iOS/Android build or contact a live host, so on-device behavior, third-party provider acceptance, platform review status, and remote connectivity are runtime unverified. All "implemented" rows mean a reachable native UI action plus a wired client path, not a successful live execution.

Use immutable source links throughout: `https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/<path>#L<start>-L<end>`. The snapshot includes React Native iOS/Android (`apps/mobile/package.json`) rather than a mobile web wrapper. ### Candidate LUNA mobile requirements (recommendations, **not** asserted current LUNA gaps)

1. **P0: One host-owned thread model across desktop and mobile.** The phone should subscribe to environment/project/thread shells and detail, preserve offline drafts/outbox content, and execute lifecycle/send/interrupt/approval commands on the host with read/operate scopes. Surface reconnect and permission states clearly. This underpins every other workflow; T3's mobile route and shared command path above are the reference.
2. **P0: A complete remote chat loop.** Mobile new task should select project/host, workspace/branch, provider/model/effort and permission mode, send attachments/context, stream transcript/tool output, answer live approvals and questions, and stop/queue/steer/restart work where the host supports it. Define explicit feature/capability flags and disable invalid actions instead of silently sending unsupported commands.
3. **P1: Thread management and long-running work.** Search/filter by host/project; archived list; rename/delete/restore; pin/settle/snooze if LUNA adopts those semantics; queue inspector with edit/reorder/remove/resume; agent list with child navigation. Treat T3's settle/snooze semantics as product choices, not requirements of remote control itself.
4. **P1: Remote workspace inspection and action.** Host file browser with read-only previews, diff review and comments, terminal read/operate separation, Git state and worktree controls. Gate each by actual host scopes and capabilities; mobile should never assume these are phone-local resources.
5. **P2: Operational and automation surfaces.** Multi-host connection selector/status, usage/limits, notifications/deep links, provider account state, scheduled task list/create/edit/run/pause/delete. Include server-authoritative ownership, validation, and version skew. T3's scheduled task editor is a concrete mobile implementation, while MCP server configuration is a deliberate separate question.

Suggested proof when implementing LUNA: one repeatable phone-to-host E2E journey creates a task in a selected checkout, receives a streamed tool result, queues and reorders a follow-up, answers a question, opens the resulting diff/file, disconnects/reconnects and confirms no duplicate send. Save a trace with host ID, thread ID, exact command IDs, connection mode, screenshots/video and post-run server state. That would verify behavior this static T3 audit cannot.
