# T3 Code remote architecture and host lifecycle

Source snapshot: `pingdotgg/t3code` at `a8bdfdb54181fb5c9d43f2747112c137a804d016` (read-only inspection, 2026-10-11). This lane covers the execution boundary and end-to-end command/stream path. It does not claim a live app or network test. Links below pin the exact source revision. T3's internal and user docs are supporting evidence; code is the primary evidence when the two overlap.

## Executive architecture model

T3 defines an **environment** as one running server plus the machine, filesystem, provider credentials and durable state it owns. Projects and threads are environment-local. Web, Electron's renderer, and React Native mobile are clients. A remote route changes only how a client reaches that server: direct LAN/public URL, tailnet, SSH port-forward, or T3 Connect's managed tunnel. A mobile phone does not become an execution host or copy the workspace. The server holds provider processes, terminal sessions, Git and files; the phone presents state and sends authenticated commands. This ownership rule is explicit in [architecture docs](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/overview.md#L3-L18) and [remote docs](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L3-L14), and visible in the common server WebSocket command handlers and server-side effect worker cited below.

```text
Mobile UI / Web UI / Desktop renderer
  -> environment-scoped shared client runtime
  -> route preflight and credential preparation
  -> authenticated HTTP + WebSocket RPC to one environment
  -> server RPC scope middleware and command intake
  -> serialized orchestrator decision
  -> transactional event/projection/receipt/effect-outbox commit
  -> server effect worker -> host provider/terminal/Git/files
  -> stored-event shell/thread subscriptions -> client projection/cache/UI
```

The hosted web client is also direct-to-environment: its connection catalog stays in the browser, and app.t3.codes does not proxy application traffic. The same distinction applies to T3 Connect: its relay brokers linking and tunnel allocation but ordinary HTTP/WebSocket sessions go through the environment's tunnel hostname, not through the relay Worker ([remote docs](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L58-L69), [Connect docs](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/t3-connect.md#L1-L11)). This matters for a LUNA design: a hosted rendezvous service need not be the application data plane, but the host must be reachable and authorized over its selected route.

## Concrete command-to-render trace

1. **Mobile owns presentation and temporary intent.** `apps/mobile/src/connection/runtime.ts` composes the same `Connection.layer` used by other clients with mobile network/storage/lifecycle services and shell/thread snapshot loaders ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/runtime.ts#L19-L60)). Mobile's thread state is instantiated from shared `createThreadEnvironmentAtoms` and shared state atoms, keyed by environment and thread ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/state/threads.ts#L14-L48)). Its outbox drain calls `threadEnvironment.startTurn` with the target `environmentId`, stable command/message IDs and `creationSource: "mobile"` ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/state/use-thread-outbox-drain.ts#L908-L940)). This establishes a real mobile command path; it does not establish that every mobile action works in a live install.
2. **Shared commands cross the wire.** `startTurn` maps to `startThreadTurn` in shared `threadCommands.ts` ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/threadCommands.ts#L278-L283)). That operation first persists/rewrites attachments, then uses `launchThread` for a new-thread/worktree bootstrap or `dispatchCommand` with `message.dispatch` for existing work ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/operations/commands.ts#L628-L711)). The shared RPC boundary looks up the **current** environment session at execution time and performs a client permission guard before calling the socket method ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/client.ts#L131-L208)). The server remains authoritative.
3. **The server admits an authorized RPC.** The WebSocket endpoint requires exact orchestration protocol compatibility and authenticates the upgrade, then installs `RpcAuthorization.layer(session.scopes)` for the RPC server ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L3140-L3178)). The exhaustive method-to-scope map marks `dispatchCommand` and `launchThread` as `orchestration:operate`, while shell/thread subscriptions are `orchestration:read` ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/auth/RpcAuthorization.ts#L38-L63)). The handler pushes a command through startup's queue and `ThreadMessageIntake.dispatchCommand`, then returns a sequence number ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L1815-L1864)). This is a receipt for accepted intent, not proof the provider finished.
4. **The host commits intent before executing.** The orchestrator plans events/effects and calls `EventSink.commitCommand` ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/Orchestrator.ts#L10970-L10992)). `EventSink` reserves a command receipt idempotently, appends events, updates projections, enqueues effects, and writes the accepted receipt in one database transaction; it publishes after commit ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/EventSink.ts#L527-L590)). For a started provider run, an effect with type `provider-turn.start` is planned ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/Orchestrator.ts#L5549-L5557)); the effect worker invokes `providerTurnStart.start` on the host ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/EffectWorker.ts#L152-L164)). The architecture doc explicitly distinguishes command acknowledgement from later provider/checkpoint completion ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/overview.md#L53-L70)).
5. **Clients reconcile persisted state.** The server exposes separate `subscribeShell` and `subscribeThread` RPC handlers ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L2031-L2040)). Thread subscriptions take `afterSequence`, read stored events, and can resume from a cursor; shell subscriptions build a snapshot from persisted project/thread state ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L744-L800), [source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L940-L981)). The client thread state attempts an HTTP snapshot when it lacks cached data, sets a sequence cursor, and then subscribes to the thread stream ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/state/threads.ts#L795-L855)). The client runtime keeps offline projections readable while marking their freshness separately from transport health ([connection doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L48-L66)).

## Host and process lifecycle

* **Desktop embedded host:** Electron main chooses a backend port/exposure and starts a primary backend process; in some Windows settings it separately reconciles a WSL backend ([DesktopApp](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/desktop/src/app/DesktopApp.ts#L193-L265)). The packaged server is executed in Electron's Node mode using the backend entry path and a bootstrap file descriptor ([DesktopBackendConfiguration](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/desktop/src/backend/DesktopBackendConfiguration.ts#L586-L612)). Main owns that child process's scope and auto-stop finalizer ([DesktopBackendPool](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/desktop/src/backend/DesktopBackendPool.ts#L145-L170)). The desktop renderer is still an environment client; it can even run without a local environment because its UI is served from `t3code://` rather than the backend ([remote doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L92-L102)).
* **Manual CLI host:** `t3`/`t3 start` runs the server; `t3 serve` runs it headlessly without opening a browser and prints pairing details ([CLI source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/cli/server.ts#L15-L69)). The user guide requires the machine to remain running and reachable for phone work ([guide](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/remote-access.md#L1-L4)).
* **Background service host:** `t3 service install/status/restart/uninstall` are actual CLI commands ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/cli/service.ts#L121-L139), [source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/cli/service.ts#L167-L215)). A service launcher supervises the server child and handles SIGTERM and version transitions ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/serviceLauncher.ts#L275-L387)). User documentation states Linux uses a systemd user service with linger; macOS uses a login-scoped launchd service; Windows background services are unsupported ([guide](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/background-service.md#L43-L57)). Treat these platform statements as source-documented behavior, not a test performed in this review.
* **SSH launch/forward ownership:** Desktop main can spawn SSH and launch or discover a remote server; if it launched the server, cleanup may stop it, while an already-running server survives disconnect. The renderer uses the forwarded URL through the same shared runtime ([remote doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L71-L84)). Mobile explicitly declares SSH gateway operations unsupported, so “mobile can control an SSH-accessible environment” only follows if it has some other reachable address/tunnel; it cannot establish an SSH tunnel itself in this source snapshot ([mobile platform implementation](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L220-L238)).
* **Identity across process changes:** The host persists one environment ID under its state directory, using an atomic publication/recovery path to keep a stable identity across restarts ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/environment/ServerEnvironment.ts#L84-L180)). Its descriptor reports that ID, OS/arch, server version, protocol version and capabilities ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/environment/ServerEnvironment.ts#L183-L255)). A route is not a distinct execution environment, and a repository clone elsewhere does not transfer its project/thread history ([remote doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L9-L18)).

## Connection ownership, routing and compatibility

`packages/client-runtime` owns one supervisor per environment. Platform layers provide storage, credentials, network status and foreground/background notifications; React views consume its state ([connection doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L1-L7), [registry service](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/registry.ts#L93-L155)). The registry maps entries by `EnvironmentId` and supports registration, route removal/reorder, environment enable/disable and retry. This enables concurrent saved connections without confusing a route with a machine. Each environment still owns its own settings, projects and work; “all environments” is an explicit action on connected hosts, not a global persisted setting ([architecture doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/overview.md#L44-L51)).

The driver orders routes and preflights direct ones using a public environment descriptor **before** preparing credentials. It checks the environment ID to reduce the risk of sending a bearer token to a different machine that acquired an old LAN address. It attempts other routes after failures, while a protocol-incompatible server stops the route walk because all routes target the same environment ([driver](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/driver.ts#L68-L135), [descriptor check](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/driver.ts#L144-L185)). The bearer authorization service independently verifies the direct endpoint but caches a same-URL/environment descriptor for ten seconds; a reassignment inside that cache window is a residual risk before it requests a WebSocket ticket with the bearer credential ([authorization service](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/authorization/service.ts#L142-L204)). Relay routes use DPoP authorization; paired direct routes use stored bearer credentials; SSH resolves through the platform gateway ([resolver](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/resolver.ts#L120-L209)). The internal doc describes learned LAN/tailnet routes and preflight of a preferred route while using a fallback ([remote doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L31-L53)).

The supervisor is the sole retry owner. Transient retries use jittered exponential backoff capped at five minutes; auth/offline blocks await a wakeup. Mobile's `AppState` and Expo network listeners wake it on foreground and network changes, including Wi-Fi-to-cellular changes ([supervisor](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L132-L145), [mobile platform](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L43-L155)). The shared connection doc explains the exceptional long-background resume: replace a possibly stale socket immediately instead of trusting a probe ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L9-L26)). It also says reconnect does not replay mutations automatically; each operation owns its retry/idempotency rules ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L82-L87)). Mobile's persisted outbox and stable command IDs are one such operation-specific strategy ([mobile call](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/state/use-thread-outbox-drain.ts#L908-L949)); the server's receipt deduplication is the corresponding admission primitive ([EventSink](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/EventSink.ts#L530-L544)).

Protocol version `2` is declared in contracts and sent on socket URLs; a mismatched WebSocket request receives HTTP 426. The client uses the descriptor to distinguish a newer server from an older one and may offer host update when advertised ([contract](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/contracts/src/environment.ts#L12-L16), [client compatibility](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/compatibility.ts#L9-L42), [server gate](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/ws.ts#L3140-L3152)). Within a protocol version, descriptor capability flags gate optional features across independently updated web, desktop, mobile and host releases ([descriptor implementation](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/environment/ServerEnvironment.ts#L208-L255), [architecture guidance](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/overview.md#L16-L38)). A socket opening is not considered ready until the initial server configuration subscription arrives ([connection doc](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L48-L55), [client session](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/rpc/session.ts#L220-L245)).

## Candidate LUNA implications to evaluate against LUNA code

These are **proposed capability boundaries**, not asserted LUNA gaps. The parent comparison must verify each against LUNA's current implementation before promoting it to a pending item.

1. Define a durable execution host identity separate from connection URL, repository clone identity, or client account. Persist it atomically, and make every project/thread lookup and command explicitly environment-scoped.
2. Give the host a network-facing authenticated HTTP/WebSocket service that owns provider processes, filesystem, Git, terminal and orchestration state. Desktop may embed/spawn it, while a separate headless/background entry point can keep remote work alive when the desktop window closes.
3. Share one environment-scoped client connection runtime across macOS, web and iOS: saved route catalog, credential storage, descriptor preflight, supervisor, initial-config readiness, reconnect and cache/projection rules. Mobile-specific code should provide lifecycle/network adapters and UI rather than a divergent protocol implementation.
4. Model direct LAN/tailnet, SSH, and cloud tunnel as routes to the **same host identity**. A route switch must validate identity, prepare appropriate credentials, and preserve the active working session until the preferred route is ready. Explicitly decide whether iOS needs SSH itself; T3 does not provide it there.
5. Make a remote send robust to interrupted connectivity: stable command ID, host-side deduped accepted receipt, committed event/cursor, operation-specific client outbox/resend policy, and a separate completion state. Never infer provider execution from an RPC acknowledgement.
6. Separate low-cost shell listing from detailed thread events, support initial snapshots plus cursor resume, and label cached offline content distinctly from live content. Keep stream replay/cursor atomic with applied state so stale or canceled loads do not skip events.
7. Enforce permissions at the host RPC boundary, including read versus operate and sensitive settings/file operations; use client permission data only to shape UI. Negotiate protocol and optional capabilities so independently updated mobile and host releases fail visibly or gracefully.
8. Make host lifecycle an explicit product feature: local desktop spawn, headless manual run, user service start/status/restart/update, and clear display of host sleeping/offline state. If a tunnel/rendezvous is built, keep its identity/link lifetime distinct from the host process lifetime.

## Failure modes and explicit unknowns

* A phone cannot reach a sleeping/stopped host. `t3 connect` can save linkage while stopped but cannot make it serve; the user guide requires `t3 serve` or service installation ([guide](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/remote-access.md#L1-L26)).
* A LAN address can point at another machine on a new network. The public descriptor preflight and authorization identity check reduce accidental credential delivery to an environment-ID mismatch ([driver](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/driver.ts#L144-L161), [authorization service](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/authorization/service.ts#L142-L204)). A silent route may later be attempted after others fail, and authorization may reuse a descriptor cached for ten seconds; avoid treating these checks as an absolute credential-leak prevention guarantee.
* An authenticated WebSocket does not imply command authority; RPC scopes are checked on each method. Authorization failure is a blocked state rather than an endless transport retry ([scope map](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/auth/RpcAuthorization.ts#L38-L63), [supervisor](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/packages/client-runtime/src/connection/supervisor.ts#L932-L949)).
* An accepted command may be followed by provider failure; a generic dispatch error may even arrive **after** commit, leaving its acceptance uncertain. The intake code marks only a fixed set of errors as definitely unaccepted ([source](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/server/src/orchestration-v2/ThreadMessageIntake.ts#L14-L30)). Stable command receipts plus event readback are needed to resolve uncertainty.
* A network change can leave the old socket apparently open. Mobile emits path-change wakeups, and long background resumes replace the session ([mobile code](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/src/connection/platform.ts#L85-L155), [connection design](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/connection-runtime.md#L19-L26)).
* Updating a desktop or service-hosted server can interrupt provider turns and remote clients. T3's service guide warns of this, while the connection runtime handles the resulting disconnect ([guide](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/user/background-service.md#L23-L30), [remote design](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/docs/internals/remote.md#L86-L90)). Exact update handoff behavior is another research lane.
* This review did **not** run the host, inspect a mobile binary, connect to the relay, exercise a user account, or execute tests. Existing test files and docs indicate intended behavior but are not runtime evidence. It did not measure reconnect latency, notification delivery, route priority under real networks, update downtime, or platform service behavior. The inspected mobile source declares app version `2.0.0` ([app config](https://github.com/pingdotgg/t3code/blob/a8bdfdb54181fb5c9d43f2747112c137a804d016/apps/mobile/app.config.ts#L228-L235)); this source snapshot alone does not prove those features are in the currently stable App Store or Play Store release. Mobile feature parity outside the architecture path, tunnel security details and LUNA's actual implementation are delegated to other lanes. Avoid turning these unknowns into “works in production” claims.
